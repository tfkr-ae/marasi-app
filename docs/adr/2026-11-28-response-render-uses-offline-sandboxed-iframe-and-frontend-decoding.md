# Response Render uses an offline sandboxed iframe and frontend decoding

Every HTTP response view in the app—the Ledger drawer, Launchpad, the Armory drawer, Logbook linked pairs, and Checkpoint held responses—offers a Render view alongside the raw HTTP editor for HTML, images (including SVG), video, and audio. HTML renders inside an `<iframe sandbox="">` (opaque origin, no `allow-scripts`, no `allow-same-origin`, no forms, no popups, no navigation) with `referrerpolicy="no-referrer"`, a strict Content Security Policy (`default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:; media-src data:`), and pre-render stripping of `<meta http-equiv="refresh">`, `<base>`, and active elements via DOMPurify before writing to `srcdoc`. SVG (`image/svg+xml`) renders exclusively as an `<img src="blob:...">` rather than inline DOM or an interactive document, which disables SVG script execution and external fetches by browser specification. Raster images, video, and audio render from revoked-on-unmount `blob:` URLs (`controls` and `preload="metadata"`, never `autoplay`). Because Marasi App runs inside a privileged OS webview with access to Wails bindings and the service control API token—and outside the researcher's proxied browser—in-app rendering must never execute untrusted scripts or emit outbound network requests that could bypass Marasi's proxy, leak the researcher's IP, or hit local/target origins. When a researcher needs live JavaScript, real origin state, or external subresources, Marasi's Browser view (`http://marasi/view/{id}`) remains the escape hatch in a proxied browser.

Response rendering preserves the exact raw bytes returned by the control API instead of decoding them lossily to UTF-8 text: `response.raw` (and Checkpoint held `raw` bytes) keep their `Uint8Array` payload so binary images, video, audio, and compressed bodies survive intact. Because Marasi stores responses dechunked but still `Content-Encoding` compressed, the frontend decodes `gzip` and `deflate` with `DecompressionStream` and `br` and `zstd` with lightweight JS decoders, capping decompressed output at 10 MiB to prevent decompression bombs and gating raw media larger than 10 MiB behind a click-to-load prompt. Content-Type headers are trusted when specific (matching `nosniff` semantics so `text/plain` containing markup is not rendered as HTML), and magic-byte or HTML sniffing runs only when `Content-Type` is absent or generic (`application/octet-stream`).

We considered three alternatives: (1) adding a Marasi control API endpoint to return decoded response bodies using Marasi's Go decoders, which would require a service API addition and would not work against older Marasi services or on live Checkpoint edits; (2) resolving external CSS and image subresources from already-captured project traffic via `/traffic` queries, which adds query fan-out latency on remote connections and mobile and is deferred until needed; and (3) allowing external subresource fetches or scripting inside an iframe or embedded browser, which contradicts the Wails webview threat model and duplicates Browser view.
