# CyberChef runs as its own UI, served by the app from its own origin

The app ships CyberChef's own web UI, built from a pinned release tag and served from the app's origin, and drives it through one adapter module that calls CyberChef's internal `window.app`. Before this, the app framed gchq.github.io in a cross-origin iframe. The browser kept the app out of that frame entirely: Marasi shortcuts didn't work inside it, it couldn't be themed or handed input, and whatever a researcher pasted left the machine. Serving it from the app's own origin lifts every one of those limits, and the frame becomes one the app fully controls.

We considered rebuilding the UI in Svelte over CyberChef's `src/core`. It would fit the app best, but it would never keep up with GCHQ's releases: every UI change upstream would have to be redone by hand. The core also only builds under webpack shims, and its npm package is Node-only. The cost of our choice is that `window.app` is internal, so GCHQ can change it in any release. The pin and the tool contract checks (`scripts/check-tools.sh`) turn such a break into a failed bump instead of a broken app. The build also leaves out the AGPL-3.0 `ua-parser-js` 2.x that the "Parse User Agent" operation uses, so no copyleft code ships.

Shipping it costs size: CyberChef v11.6.0 adds 47.8 MiB to every desktop and mobile build (without the `.gz` and `.br` copies, which the build drops). Being same-origin also means CyberChef's own localStorage would be the app's, so the build puts an in-memory Storage first in its `index.html` (`frontend/cyberchef/memoryStorage.js`, noted in `MARASI-NOTICE.txt`): its options and theme last only as long as the frame.
