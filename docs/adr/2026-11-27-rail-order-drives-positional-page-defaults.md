# Rail order drives positional defaults for built-in pages

The researcher's rail order is stored app-wide in `marasi_appconfig.yaml` (omitted when unchanged from the app's default), independent of projects and keybinding profiles. Home stays pinned at slot 1 (`⌘1` / `Ctrl+1`), the built-in pages in slots 2–8 take `⌘2`–`⌘8` (`Ctrl+2`–`8`), and `⌘9` and `⌘0` remain Connections… and Reset Text Size. Past slot 8, CyberChef and Excalidraw fall back to `⌘⇧Y` and `⌘⇧J` so uncustomized setups keep today's shortcuts, while any other overflow page has no default shortcut. On narrow phones where CyberChef is hidden, the bottom bar skips hidden pages to keep its five tabs full, while keyboard shortcut numbering stays anchored to the saved rail order so shortcuts never shift on resize.

Built-in page navigation actions (`global.go-*` below Home) use positional defaults, following [Positional extension defaults yield to other bindings](2026-10-10-positional-extension-defaults-yield.md) and [Keybinding profiles override recoverable factory defaults](2026-10-10-keybinding-profiles-override-factory-defaults.md). An explicit override in a keybinding profile stays pinned to its action id when pages move, and a moved positional default that collides with a researcher's custom binding yields (leaving that page unbound until the key is free) rather than invalidating the profile. Omitting the default rail order from config—and inserting newly added built-in pages at their default position rather than forcing them to the end—ensures future releases can place new pages wherever they belong without locking researchers into a stale list.

We considered storing rail order inside each keybinding profile, or keeping static `⌘1`–`⌘8` defaults separate from the rail. Putting layout order in keybinding profiles would tangle visual navigation with shortcut customization and surprise researchers when switching profiles; keeping shortcuts detached from the rail would break the spatial 1–8 mapping that makes reordering useful.
