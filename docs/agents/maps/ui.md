# Screens and type

Which component draws each part of the app, and the type sizes the pages share. Paths are under `frontend/src/` and names are components, functions and files, so search for them.

## The app frame

`routes/+layout.svelte` draws everything around a page:

- **App rail.** Skeleton's `AppRail`: Home stays pinned as the first direct child (`:first-child` carries the mobile safe-area inset), followed by the 10 reorderable built-in pages from `stores/railOrderStore.js` (`createRailOrderStore.js`, canonical list and resolution/projection helpers in `lib/railOrder.js`, icons in `lib/railIcons.js`, persisted app-wide under `rail_order` in `marasi_appconfig.yaml` via `rail_order.go` — omitted when default, with newly added built-in pages inserted at their canonical default index on upgrade), then one `AppRailAnchor` per extension with an interface (its Lua `icon` render, else its web component's `icon` element through `lib/extensions/WebComponent.svelte`, `data-testid="extension-web-ui-tile"`), then the pinned utility trail (Connections, light switch, Settings). On desktop (`!$mobile`, primary non-touch pointer), the 10 built-in tiles below Home reorder directly by pointer drag-and-drop (`lib/railDrag.js`: ~6px threshold so quick clicks navigate immediately, square-edged primary insertion bar `data-testid="rail-drop-indicator"` and faded dragged tile, Escape or dropping back in the original slot cancels without saving or navigating, trailing click suppressed, dropping at a new boundary calls `saveRailOrder` and reverts with an error toast on failure; no permanent drag handles or right-click menu). Three icons carry an indicator: Settings shows the update dot (`settingsIconIndicator`), Checkpoint the count of intercepted items (`checkpointBadge.js`, `data-testid="checkpoint-badge"`), and Armory the runs in progress (`lib/armory/armoryBadge.js`, `data-testid="armory-badge"`, from the store's active set through `activeCountsOf`); both counts go in the icon's title too.
- **Connection tile & Connections modal.** `lib/connection/ConnectionRailTile.svelte` (in the rail's trail above the light switch) and `BottomBar.svelte` (Connections tab on narrow mobile) show the active connection (`connectionStore`) with a status dot (`lib/connection/status.js`: labels and colours per phase, `data-testid="connection-tile"`, `data-phase`) and a subtle primary indicator dot (`connectionTileIndicator` in `lib/connection/indicators.js`) whenever the active connection has an available service update, a pending restart, or (on desktop local) a proactive carried-CLI upgrade. Clicking it or running the Marasi menu's "Connections…" action (`global.connections`, ⌘9 / Ctrl+9, `keybindings-and-menus.md`) opens the Connections modal (`ConnectionsModal.svelte`, registered as `Connections`; `connectionsModal()` in `lib/connection/modal.js`), which is the single place for managing connections on desktop and mobile — `Settings → Connection` is removed, and legacy `?section=connection`, `?section=cli`, and `?section=updates#cli` links open the Connections modal (`lib/settingsSection.js`). The modal's connection list ends in Add connection (`AddConnection.svelte`: a local connection for a named instance, picked from `LocalInstances` or typed, with an optional proxy port (`localPort.js`); or a remote from a pairing payload, `pairing.js`, or name, address and password). `ConnectionDetail.svelte` (`lib/connection/detail.js`) uses an action-first layout: a compact header (name, status dot + label, mono host/instance/OS line, and `Marasi <version> (<channel>) · API <level>` when connected), a top action bar (`Check update` / `Update to <version>` / `Install <carriedVersion>` / `Restart to apply`, `Restart`, `Stop` / `Start` / `Retry` / `Switch`), a single contextual slot directly below the action bar (`ConnectionContextSlot.svelte` + shared `ConnectionInlineError.svelte`, with strict precedence via `contextualSlotKind` and `contextualSlotErrors`: inline restart/stop confirmation, auth/CLI-missing/outdated/stopped/failed states, inline 4-step service-update progress tracker with Cancel until swap, restart-required tracker, desktop-local carried CLI upgrade, available release notes + Release page link, desktop-local channel mismatch note with one-click switch, and update/restart/stop/API errors), operational rows (`Project`, `Access` via `ConnectionAccess.svelte`), a collapsed setup disclosure (`ConnectionSetupDisclosure.svelte`: `Update channel & reinstall` on remotes; `Channel, CLI path & quit behavior` on desktop local with service channel, reinstall, local CLI path, manual carried CLI, and `When quitting Marasi App` via `localCLIStore.setWhenQuitting`), and management rows (`Address`/`Remove` on remotes, `Proxy port`/`Remove` on added locals; `manage.js`, `removeBlock` in `status.js`). With no Marasi CLI the detail shows `CLISetup.svelte`, and the modal opens by itself. The start screen's **Connections…** (`data-testid="startup-connections"`, `+layout.svelte`'s `openConnections`) opens it before the app has loaded. `Settings → Updates` is desktop-only (`MOBILE_HIDDEN_SECTIONS`) and strictly for Marasi App updates (`updates.md`), with no Marasi CLI or service-update rows. `ConnectionBanner.svelte` (over the page) shows unhealthy states (`reconnecting`, `failed`, `stopped`, `switching`, `restarting`, `project-changed`, `apiWarning` with a `Connections` button), inline restart confirmation, and dismissible `restart-required` and desktop-local `carried-upgrade` strips (`connectionActionBanner` in `lib/connection/indicators.js`); it also wires `createRestartHeldHandler` (`lib/checkpointHeld.js`, opening `checkpointHeldModal` on `409 checkpoint_items_held`), connection toasts (`connectionToasts.js`), and service-update toasts (`serviceUpdateToast`).
- **Marasi menu.** `GlobalMenu.svelte` (in `lib/components/MarasiMenu/`) is mounted once here. It runs the `global.*` actions, such as going to a page. ⌘K opens `MarasiMenu.svelte`: a square-edged dialog with the search field (`id="commandmenu"`), on a page that mounts one a red (primary) heading named after the page with the page's groups, a sand (tertiary) Marasi heading with a bar and fading rule, one row per menu group (tinted icon tile, label and description, count badge, key badge, chevron) and loose actions aligned to the same right edge, and a footer with the highlighted row's description and real shortcut. `MenuKeys.svelte` draws its key badges (1.5rem, system font). `GlobalMenu` mounts the one for Home and Settings (only the Marasi section). Every page with its own menu mounts its own `MarasiMenu` (its section, then the Marasi section), and the WebSocket modal mounts an overlay-tier one. See `keybindings-and-menus.md`.
- **Modals.** Components are registered by name in `modalRegistery` and opened with `modalStore.trigger({ type: "component", component: "<name>" })`. Most are `lib/components/*Modal.svelte`. Skeleton's built-in `confirm`, `alert` and `prompt` modals take the type scale from the `<Modal>` props here (`regionHeader`, `regionBody`, and `btn-sm` in `buttonPositive`/`buttonNeutral`).
- **Drawer.** `AppDrawer.svelte` is the Skeleton drawer that Compass, Checkpoint and Workshop open through `drawerStore`. The Ledger has its own drawer instead (see `ledger.md`), and so does the Armory: `lib/armory/ArmoryDrawer.svelte` and `ArmoryDrawerRail.svelte`. Both details columns draw the facts with `lib/ledger/DrawerFacts.svelte` and the Linked section with `lib/ledger/DrawerLinked.svelte` (the Armory passes `onUnlink`). The Armory page reports whether it is open to the menu contexts through `armoryDrawer` in `lib/keybindings/app.js`.
- **Interactsh.** It is loaded the first time its rail icon is clicked or `global.go-interact` runs (`interactActivator` in `lib/interact.js`), then stays mounted in the layout, so it keeps its state. Its route only shows or hides it. It is the only tool the layout mounts: CyberChef and Excalidraw are ordinary pages (see `tools.md`), so they unmount when you leave, and their documents live in `lib/tools/documents.js`. `/sveltechef`, CyberChef's old path, redirects to `/cyberchef` (`routes/sveltechef/+page.js`).
- **Opening screen and toasts.** `OpeningScreen.svelte` (see `project-open.md`) and Skeleton's `Toast`.
- **The page** renders in `{#key $pagesKey}<slot />`.

A new built-in page needs a route, an entry in `BUILTIN_RAIL_PAGES` (`lib/railOrder.js`) and `RAIL_ICONS` (`lib/railIcons.js`), and a `global.go-*` action in the catalog (and `GlobalMenu.svelte`). `+layout.svelte` and `BottomBar.svelte` derive their tiles from `railPages`. If it has its own shortcuts, it also needs a context in `contexts.js`.

## Mobile (iOS and Android)

`lib/platform.js` asks Go for the OS once (`platformOS` in `runtime.js`). `platform` is `"ios"`, `"android"` or `"desktop"`; `mobile` is true for both phones, and the root element gets the `mobile` class and the platform's name. Use `mobile` for anything about layout, touch, or what a phone can't run (the Marasi CLI, Chrome, the updater: `MOBILE_HIDDEN_ACTIONS`, `MOBILE_HIDDEN_SECTIONS`); use `platform` only where the two phones differ (the share sheet, the QR scanner). The desktop never takes either path.

- **Where the styles are.** A component's mobile layout is in its own `<style>`, as global `html.mobile …` selectors (the Logbook record's header in `LogbookRecord.svelte`, the Messages modal's tabs in `lib/messages/MessagesModal.svelte`). `app.css` keeps only what several share: touch and selection, the resize handles, the maximised Ledger and Armory drawers (`.mobile-fullscreen`), the settings rows, and the modal, drawer and toast sheets.
- **Narrow layout.** Under 40rem (`COMPACT_QUERY`, the iPhone Duo folded, a phone) `BottomBar.svelte` replaces the app rail: `projectBottomBar` (`lib/railOrder.js`) derives Home plus the first 4 visible built-in pages from the resolved rail order (5 tabs total, skipping hidden CyberChef when `!$chefShown` so the bar stays full while shortcut numbering stays anchored to the saved rail order), Connections, and More, a sheet with the remaining visible built-in pages in rail order, GUI extensions, Settings and the Color Scheme tile. It publishes its height as `--bottom-bar-height`. Side-by-side panes become tabs with `PaneTabs.svelte` (the hidden pane gets `.pane-off`), and a dock closes when a row marked `data-dock-pick` is tapped (`Dock.svelte`).
- **Insets.** Use `--safe-top`, `--safe-right`, `--safe-bottom` and `--safe-left`, never `env(safe-area-inset-*)`: Android's web view reports env() as 0, so the app sets the variables there. The mobile rail's width is `--mobile-rail-width`.
- **Sheets.** Every modal, drawer and the Marasi menu fills the screen but leaves the bottom bar or rail in view and usable, except over a maximised drawer (`.mobile-fullscreen`), which already covers them (`isolateOverlays`'s `live` option keeps them out of the inert app). A nav tap or a swipe down (`swipeToClose.js`) closes the top sheet through `closeTopOverlay()` in `overlayIsolation.js`, as Escape does, so a modal with an Escape handler (`interceptModalEscape`) can ask about unsaved edits first; the nav tap then goes nowhere.
- **The phone's text size.** Android's Font size and iOS's Text Size scale the root font size on top of Text size (`lib/systemTextScale.js`, `systemTextScale` and `textScale` in `stores/textSizeStore.js`), so spacing grows with the text. Android keeps the web view's text zoom at 100%, which grew only the text, and `MarasiAndroid.textScale()` (`MainActivity`) answers how much the Font size grows 16sp; the activity restarts when it changes. iOS reads a hidden `-apple-system-body` probe (17px at the default size), which WebKit resizes on a change, so it applies live. The scale is held to 0.8–2. Anything sized from Text size reads `textScale`, not `$textSize.scale`.
- **Touch.** `lib/touch.js`: a long press opens the context menus, the keyboard stays down under modals, and a two-finger swipe down opens the Marasi menu (`lib/menuSwipe.js`, installed on the app's window and inside CyberChef's frame).
- **Pairing.** A phone runs no local connection: `connectionStore.start({ remoteOnly })` reaches the first saved remote, or waits in the `unpaired` phase, where the start screen says to pair and Connections opens on `PairConnection.svelte`. iOS scans the QR code in a viewfinder inside the page (`QRScanner.svelte`, `qr_scan_ios.m`); Android opens a full-screen scanner (`androidScan.js`, `MainActivity`'s `MarasiAndroid.scanQr`). A modal on a phone focuses itself, not its first field (`isolateOverlays`'s `quiet` option).
- **Store builds.** The iOS bundle is assembled without Xcode, so `build/ios/Taskfile.yml`'s `stamp:info-plist` writes what Xcode would: the version from `VERSION` (`build/ios/scripts/store-version.sh` turns a DD.MM.YYYY date into YYYY.M.D, so later releases sort higher on the App Store), `BUILD_NUMBER` (else the time) as the build, the minimum iOS, and the SDK and Xcode keys. Android takes `versionName` and `versionCode` from the same `VERSION` and `BUILD_NUMBER` (`app/build.gradle`), and `android:assemble:aab:release` stops without the upload key (`ANDROID_KEYSTORE_FILE`). Both pass `VERSION` and `CHANNEL` to `build_info.go`, so Settings → About shows the release. `.github/workflows/testflight.yml` (Actions → TestFlight → Run workflow) builds iOS from main on the `xcode-27` runner (an older iOS SDK puts the app in compatibility mode on the iPhone Duo; a step stops below SDK 27), signs it with the CI's own Apple Distribution certificate and "Marasi App Store CI" profile (secrets `IOS_DISTRIBUTION_CERT`, `IOS_DISTRIBUTION_CERT_PASSWORD`, `IOS_APPSTORE_PROFILE`; `build/ios/scripts/appstore-entitlements.sh` writes the entitlements from the profile), and uploads it with `asc builds upload` (secrets `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_PRIVATE_KEY_B64`, variable `ASC_APP_ID`). `release.yml` runs it for each release tag and `nightly.yml` for each nightly (channel `nightly`, against the nightly's marasi commit), beside the desktop builds; its failure leaves the release or nightly alone. A nightly's version `DD.MM.YYYY (nightly <sha>)` becomes the App Store's `YYYY.M.D`, so a release and a nightly on one day share a version and differ by build number. The build number is the UTC time (`YYYYMMDDHHMM`, the Taskfile's default), so it rises across manual and release runs. `.github/workflows/play.yml` (Actions → Google Play) builds the Android bundle on `ubuntu-latest` with JDK 21 (the Android Gradle plugin fails on newer JDKs), signs it with the upload key (secrets `ANDROID_UPLOAD_KEYSTORE`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`; alias `upload`; Play App Signing re-signs it) and uploads it with `r0adkll/upload-google-play` (secret `PLAY_SERVICE_ACCOUNT_JSON_B64`). Its version code is the minutes since 1970, since the iOS build number overflows it. Nightlies go to internal testing; releases go to the track in the variable `PLAY_RELEASE_TRACK` (internal until it is set; `alpha` is closed testing).
- **Android.** `build/android` is Wails' template with Marasi's changes marked `Marasi:` in `MainActivity.java` and `WailsBridge.java`: the safe-area variables, Back (`androidBack.js`), plain-HTTP calls from the https page, the QR scanner, and Save As through the share sheet (`share_file_android.go`). `env_android.go` gives the process a `$HOME` and sends Go's log to logcat (tag `Marasi`); passwords go to Android's secure storage (`keychain_android.go`). Neither phone runs the updater (`mobileApp`).

## Editors

Every code editor is `svelte-codemirror-editor`'s `CodeMirror`:

- `lib/logbook/RequestPair.svelte` shows a finding's or test case's linked request and response with the Ledger's `DrawerEditor`, in the Logbook's record view and in `RecordModal.svelte`, the finding and test case modal (registered as `LogbookRecord`; see `logbook.md`).
- `lib/ledger/DrawerEditor.svelte` is the Ledger drawer's editor.
- `LedgerQueryBox.svelte` is the Ledger's query editor.
- `LaunchpadWorkspace.svelte` holds the Launchpad draft.
- `WebSocketInject.svelte`, `WebSocketCheckpoint.svelte` and `WebSocketMessagesTable.svelte` are the WebSocket editors.
- `lib/checkpoint/ItemWorkspace.svelte` holds the intercepted item and its context; `lib/checkpoint/RulesEditor.svelte` holds the Checkpoint rules.
- `lib/extensions/components/Editor.svelte` is the editor an extension interface gets.
- `lib/armory/TemplateEditor.svelte` holds the Armory request template (opts into Armory overlays and framed message-form body highlighting via `httpHighlighting({ mode: $marasiConfig.SyntaxMode, armory: true, framing })`).
- Compass and Workshop create their own in the route file.

Raw HTTP is highlighted with `lib/httpHighlight.js` (`httpHighlighting({ mode: $marasiConfig.SyntaxMode })`) backed by `lib/httpHighlight/` (`headParser.js`, `bodyParsers.js`, `formParser.js`, `resolveBody.js`, `armoryOverlay.js`, `framedBodyParser.js`), a shared Lezer HTTP language that parses HTTP/1.1 and Marasi's HTTP/2 text form (GLOSSARY Protocol) and mounts body parsers through `parseMixed`, honoring `SyntaxMode` (`auto` always highlights the head and skips body highlighting at 75,000 characters, `enabled` highlights all, `disabled` highlights nothing). Import it rather than `@codemirror/legacy-modes/mode/http`. The Lua editors' autocomplete is `lib/autocomplete/` (see `marasi-service.md`, Marasi source, for keeping it in step with Marasi).

A shortcut typed in an editor runs after the editor has handled the key (see `keybindings-and-menus.md`).

## Type scale

The type scale is Tailwind's rem sizes plus two dense sizes, `text-2xs` (0.6875rem) and `text-3xs` (0.625rem), defined in `tailwind.config.js`. The theme (`tfkr-theme.js`) sets only the font, `system-ui`. Text size (`lib/textSize.js`), and on a phone the phone's own text size, scales the root font size, so every size below scales with it:

| Use | Classes |
|---|---|
| Page and modal titles | `text-base font-bold` |
| Section headings | `text-sm font-bold` |
| Body text, menus, toolbars, buttons | `text-xs`, with `btn btn-sm` for buttons |
| Dense table rows, labels, metadata, rail labels | `text-2xs` (the Ledger table sets `font-size: 0.6875rem` in its own style) |
| Paths, ids, log lines | `font-mono text-2xs` |
| Counts, badges, group labels | `text-3xs` |

**Exception: the Marasi menu.** `MarasiMenu.svelte` and `MenuKeys.svelte` are larger than the scale on purpose, so the menu reads at a glance (the menu redesign spec): `text-sm` rows and search field, `text-xs` descriptions and counts, and 1.5rem (`h-6`) key and count badges. Leave those sizes as they are, and don't copy them elsewhere. The Keybindings settings are not part of the exception.

Write every text size in rem, including CodeMirror `fontSize` styles. `lib/textSizeRem.test.js` fails on a text size in px and names its file and line.

Marasi is square-edged. `lib/squareEdges.test.js` fails on any `rounded*` class or CSS radius except `rounded-none`, `rounded-0` and `rounded-full` on a dot of at most `h-4 w-4` (other circles go in its `CIRCLES` list with a reason). The theme pins Skeleton's radius tokens to 0px, and `app.css` squares `btn-icon` and `badge-icon`.

Action buttons (`btn`, `btn-icon`) take their variant from `primaryVariant($modeCurrent)`, or `tertiaryVariant`/`neutralVariant`, in `lib/launchpad/format.js`: no other Skeleton `variant-*` and no border or ring. `lib/buttonVariants.test.js` checks them; its `GRANDFATHERED` list holds the existing exceptions.

`app.css` adds the denser `.btn-group-sm` and `.table-dense`. To match the scale, copy from `LedgerTable.svelte`, `DrawerCommandStrip.svelte`, `DrawerLeftRail.svelte` or `OpeningScreen.svelte` instead of measuring.
