# Startup and opening a project

How the app starts on the service's project and switches to another one, across Go, the layout and the stores. Names are functions, stores and files, so search for them. For anything inside one function, read the function.

## Startup order

1. **Go.** `main` registers `App` as the Wails application's service, so Wails calls `App.ServiceStartup` before the window loads. `NewApp` builds the Marasi proxy and calls `newApp`, which tests call directly. `newApp` wires the project lifecycle and the `configure*Handlers` events. `ServiceStartup` opens no project and starts no listener.
2. **Layout.** `StartupRoutine2` in `frontend/src/routes/+layout.svelte` runs `readConfig` (in `frontend/src/stores.js`), then `connectionStore.start()`, and resolves when `loadedProject` is set. Until then the start screen shows `startupText` (`lib/connection/status.js`): "Connecting to <name>…" for a remote, "Starting Marasi…" or "Connecting to Marasi…" on Local. On failure it shows the error and Retry. While starting, connecting or failed (`startupOffersConnections`), it also offers **Connections…**, which opens the Connections modal over the start screen. Switching there before the first load starts the new connection, and the switch's reload loads its project.
3. **The service.** The connection store starts or attaches to the local instance (`ConnectLocal`), reads `/service/status`, opens `/events`, and loads whatever project the service has open: the scratchpad (`<config dir>/projects/scratchpad.marasi`) on a fresh instance. Its `loadProject` (`stores/connectionStore.js`) runs `projectStore.loadService(path)`, which runs `loadProject` in `stores/projectStore.js`, then names the project and sets `loadedProject` (see `marasi-service.md`, "Moving onto the service"). The app never opens the scratchpad itself.
4. **After the first load.** `StartupRoutine2.then` installs the menu shortcuts and subscribes to Go's update events and the Checkpoint abandon toasts; every page's data comes from the service's `/events` through its store. Go starts no listener, and the first-run listener setup no longer shows.

## Opening and switching

The flow is `open(target)` in `stores/createProjectStore.js`, over `projectApi.js` (the service client) and bound in `stores/projectStore.js`. `projectStore.test.js` runs it against a fake client. A target is `{name}` (a project in the service's `projects` dir) or `{path}` (an absolute `.marasi` file); `projectTarget` turns what the picker gives into one: a listed project (the Project modal's `{name, path}` from `listProjects`, or the opening screen's `{path}`) opens its exact path, since recents and named projects can share a name; typed text opens by path when it holds a separator, else by name.

- **Held Checkpoint items.** A switch is refused while Checkpoint holds an item, because the service would wait for it with nothing on screen to say so. `openProjectPicker` in `globalActions.js` shows the refusal (`checkpointHeld.js`) in place of the picker, from `projectStore.held()`. `open` reads `GET /checkpoint` again first, for an item held after the picker opened, and resolves `{status: "held", ids}`, which `globalActions.js` shows as the same modal.
- **Unsaved work.** `open` then asks Go's `ConfirmProjectSwitch` (`confirmLosingWork`: unsaved Launchpad drafts, active Armory runs). A no resolves `{status: "cancelled"}` and shows nothing. Go knows the runs only from the frontend: `armoryStore.js` reports their number (`SetActiveArmoryRunCount`), and on a yes Go sends `armory-cancel-runs` and waits for `ArmoryRunsCancelled` (`armory_guard.go`); quitting asks the same way.
- **The service.** `POST /project/open` is synchronous and returns the canonical path. A refusal leaves the service's project as it was: `409 project_already_open` reads as `project_locked` (`lib/service/errors.js`), and `project_busy` (an Armory run) as any other failure.
- **Opening screen.** `open` keeps the screen's state in the store (`opening`, `shown`), exported as the `opening` and `openingShown` stores. It shows the screen after `openingDelay` once the prompt is past, so a quick switch never shows it, and at once on a failure. Its pure logic is `lib/openProgress.js`, drawn by `OpeningScreen.svelte`. Steps come from the service's `project.*` events (`withProjectEvent`): `project.opening` (Open), `.upgrading` (Upgrade, with the migration and `applied/total`), `.waiting` (Wait, naming what the service waits for), `.opened` (Load), and `.opening_failed` (its reason goes to Details, also after the refusal). Events for another path are ignored; an open by name takes its path from the first event for that name. The load reports its parts through `part(signal)` (`loadSignals`).
- **Failure.** The screen lists the service's projects (`GET /project/list`) to open instead. With them come the active connection's recent projects (`RecentProjects`). Browse… (the native file picker) shows only on the local connection (`filePickerShown` in `lib/connection/status.js`), here and in the Project modal; a remote opens from its list or a typed path. `stay()` keeps the loaded project, or the target when it opened but didn't load; `retry()` re-runs the last target.
- **Another client's open.** `follow({opened, failed})` keeps a standing `project.*` listener through the service client (so it outlives stream resumes; replayed events act as live ones), installed at the top of `onMount` in `+layout.svelte` with the failure toast (`Couldn't open <project>`). Events are ignored while the app's own open or reload is under way and still live (`own`, that run's `live()`; a superseded run, as after `leave()`, never mutes the next session), as are late ones of its own failed open whose screen still shows. Another project's `opening`/`upgrading`/`waiting` shows the opening screen after `openingDelay`, kept down while the service waits for Checkpoint items (the screen would cover them). `opened` hands the path to `connectionStore.followSwitch`, which reads `/service/status` (a replayed switch since undone does nothing), closes the stream and asks Go's `ConfirmFollowProject(project)` (`Another client opened <project>.`, buttons `Stay` and `Load <project>`), which names the unsaved Launchpad drafts and Logbook edits the frontend reports. Load is `reload(path)`; Stay is the reconnect's declined-load state (see `marasi-service.md`, "Reconnect") and `closeFollowed()` takes the screen down. `opening_failed` closes the screen and keeps the pages. Only a `connected` store follows, so a reconnect's own load never doubles it.
- **Load and pages.** After the switch, `loadProject` (`projectStore.js`) resets every store (`resetProject` in `stores.js`), then `projectData.load` (`stores/projectData.js`) clears every registered store and runs every store's load together (`allSettled`, as its `resync` does), so a remote open costs about one round trip for the data, not one per store. The opening screen's part is the earliest store still loading: each store's `part(signal)` is reported in registration order once every store before it has settled. One store's failure stops none of the others; once all have settled, each failure is logged and the load rejects with the first in registration order, which fails the open as before. Stores whose load makes several independent reads make them together (Armory: templates, wordlists and active runs; Launchpad: the list and the pending launches). `open` then bumps `generation` (`pagesKey`), which remounts the pages, and `globalActions.js` goes to `/` and toasts. `reload(path)` runs the same load, opening screen and remount without an open or a prompt, for a reconnect that found another project or a restarted service, or another client's open (the connection store asks first; see `marasi-service.md`, "Reconnect"). Each `open`, `reload` and `loadService` is a run (`claim`), bound to the service client's connection when it begins (`api.bind()`; see `marasi-service.md`, "Service client"): a newer run supersedes it, and so do the caller's `current()` turning false (the connection store passes its session check), the client leaving that connection, and `leave()`, which a new connection session calls and which also closes the opening screen and clears Try again (`projectOpenSwitch.test.js`). `loadProject(path, part, live)` hands `live` to `resetProject` and `projectData.load`, which checks it before the clear and before each store's load starts; once it is false the load reports no more parts and resolves without its failures. Dropping a late answer from a load already started is each store's job: most stores' `clear` moves them to the new project, so an older read's answer is ignored (Armory's and Launchpad's `projectStateVersion`, for example). Extensions, waypoints, WebSocket, upstream proxies and the Ledger menu counts have no such guard yet. After each await a superseded run leaves the opening screen, `loaded`, `generation` and failures to the newer run, resolves to `{status: "superseded"}`, and on ending closes its screen only while `screenOf` is still its own (`projectLoadRace.test.js`).

## Where a change goes

- Work every open needs: the service does it; the app only loads.
- Something the frontend reads per project: `projectData.register` in its `xStore.js`, with its `clear`, `load`, `resync` and `signal` (`loadSignals.x`, with its part in `openProgress.js`, so the screen tracks it). See `marasi-service.md`, "Adding a store to the service client".
- A subscription that must exist before the first project loads: the top of `onMount` in `+layout.svelte`. Otherwise use `StartupRoutine2.then`, and remove the listener in the same cleanup.
