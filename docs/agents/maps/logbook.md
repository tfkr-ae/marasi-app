# Logbook

Which files work together on the Logbook page, how a finding or test case is read, changed and saved, and where a page action goes. Names are functions and files, so search for them. A record is a finding or a test case; in the store, the kinds are `"finding"` and `"testCase"`.

## Files

- `frontend/src/routes/logbook/+page.svelte` wires everything together: the dock, the toolbar, the workspace (the summary, or the open record in its place), Edit (behind the leave prompt), Delete's confirmation, the page-local Esc, and `logbookMenu` for `useMenuActions` and ⌘K.
- `frontend/src/stores/createLogbookStore.js` is the one seam for the page and the modal. It holds the records, the filters and grouping, the open record, the edit session (`session`) and the inline fix (`fix`). Its selectors are pure functions of the state: `completenessOf` (from `ITEMS`, the required and optional items per kind), `filteredOf`, `groupsOf`, `nextOf`, `openRecordOf`, `linkedOf`, `reportOf`, `changesOf`, `isDirty`. Every write goes through its per-kind `BINDINGS` table. It takes its API as an argument: `frontend/src/stores/logbookApi.js` (`createLogbookApi(client, {saveFile})`) maps the service's routes and snake_case shapes to the PascalCase records the store keeps, and `logbookStore.js` binds it to the app's service client and registers it with `projectData` (`resync` keeps the filters, the open record, the modal's session and a fix with input). `listFindings` and `listTestCases` are one `GET /finding?full=1` and `GET /test-case?full=1`, whose items equal the per-id read. Tests: `logbookStore.test.js` (list model), `logbookEditSession.test.js`, `logbookInlineFix.test.js` (with Delete in the edit session tests), `logbookApi.test.js` (the service mapping, resync, export, over a fake client).
- `frontend/src/stores/findingStore.js` and `testCaseStore.js` are views of the Logbook store for Home's counts, the Ledger, the Armory and the Launchpad: `populate`, and `linkRequest`/`unlinkRequest`, which call the store's `linkNow`/`unlinkNow`.
- `frontend/src/lib/logbook/`:
  - the page: `LogbookToolbar` (search, kind toggles, Severity/Category/Tags menus on the Ledger's `ToolbarMenu`, Export), `LogbookOutline` (the dock's tree, create buttons, status toggle, `GroupPicker`), `LogbookSummary` (the list view);
  - the record view: `LogbookRecord` (header, Back/Next/Edit/Delete), `RecordChecklist` with `InlineFix`, `LinkedRecords`, and `EvidenceViewer` (`RequestList` + `RequestPair`, `ArtifactList` + `ArtifactPreview`). `RequestList` shows rows from `lib/logbook/pairRows.js`: the saved links in one bodyless traffic query (`listLinkedRows`, `finding = "<id>"` or `test_case = "<id>"`, no exclusion), and a link the query doesn't list (staged in an edit) read on its own, four at a time; only `RequestPair` reads the picked pair in full (`readPair`). The modal's `RecordEvidence` reads its rows the same way. The modal reuses `EvidenceViewer`;
  - the modal: `RecordModal` (registered in `+layout.svelte` as `LogbookRecord`), `RecordForm`, `RecordEvidence`, `TagInput`, `TemplatePicker`, `TestCasePicker`, `OptionList`. `recordEditor.js` opens it: `newRecord(modalStore, kind, preset)` and `editRecord(modalStore, kind, id)`;
  - export: `ExportReview` (registered as `ExportReport`) and `ReportReview`;
  - helpers: `severityColors.js` (the severity badge and mark colours, also used by `CVSSCalculator`), `artifacts.js` (content type to preview, tested in `artifacts.test.js`). The CVSS picker is `lib/components/CVSSCalculator.svelte` over `lib/cvss.js`.
- `frontend/src/stores.js`: `reportMetadata` holds the export's details, with `custom_properties.include_test_cases`; `resetProject` pre-fills Assessor from `OSUserName`.
- Go: `save_file.go`'s `SaveFileAs(title, defaultName, filterName, filterPattern, contentBase64)` saves bytes the frontend read from the service through the native Save dialog (reports, artifacts, the certificate), returning the path or `""` on cancel; `os_user_name.go`'s `OSUserName`. Tests: `app_save_file_test.go`. `reporting.go`'s old bindings have no frontend caller.

## Reading and filtering

- `filteredOf` applies search, kind, status and the contextual filters. Severity narrows to findings; category and tags narrow to test cases. `setKind` drops the filters that do not apply; All drops them all, so unpressing a kind never leaves a one-kind filter on both kinds. A kind the tester did not pick returns to All when its filters clear (`manualKind`).
- Any filter change closes the open record (`setFilters`), so the page shows the list the filters now give.
- `nextOf` follows `groupsOf`'s on-screen order, findings then test cases, and wraps. With the status filter on All, it skips Done records ("Next in progress").
- The request/response pair (`RequestPair`) and a text artifact (`ArtifactPreview`) use the Ledger drawer's `DrawerEditor` and behave as the Ledger and Launchpad editors do: syntax by `usesSyntax` and the Syntax setting, wrapping by the shared `lineWrap` store (the Ledger drawer's Wrap lines) and the Line wrapping setting. They have no wrap control of their own; a pane whose long line paused wrapping says `Not wrapped` (`.logbook-wrap-suspended`), as the Launchpad's panes do.
- A dock section's `GroupPicker` menu sits inside that section's sticky header, so `LogbookOutline` raises the header (`z-20`) while its menu is open; otherwise the next section's header, at the same `z-10`, paints over the menu.
- A checklist row clamps its text to two lines. When the text runs past them (`clamp` in `RecordChecklist`), a chevron (`data-expand`) or a click on the text shows it in full, read-only, in place (`data-expanded`). One row expands at a time; opening another record or the row's inline fix collapses it.
- Opening a record (`open(kind, id, focus)`) starts a fix on its first missing required item (`firstMissingOf`), or on `focus` when given. The fix does not take focus, so Next Record (⌘⇧]) and Esc keep working.

## Changing a record

Every change goes through the store's `saveIn`, which runs in this order:

1. A new record calls `create` (with its requests and test case), then the fields, then the uploads.
2. An existing record saves its fields, then links and unlinks each changed request, then uploads and deletes each changed artifact.

Each call that succeeds moves `original` on, so a failed call keeps the session with only what is still unsaved, and Save again carries on. An empty title makes no calls.

- **The modal.** `startNew` or `edit` copies the record to `session.draft`. Edit with an inline fix that has input goes through `guard` first, so the leave prompt asks. Nothing is written until Save; `discard` makes no calls. `requestClose` closes a clean session and asks on a dirty one (`confirming`). The modal handles its own ⌘S and Esc, since an open Skeleton modal blocks every menu action (`gate.js`). It has no `toggleAction`, unlike Export: the create keys must not close a dirty session without asking. Save's result carries `done`, and the modal then shows the same Done toast as the inline fix.
- **Inline fixes.** `startFix(item)` stages one item in the `fix` slot, and `saveFix` saves only that item through `saveIn("fix")`, then opens the next missing item. Moving away from a fix with input (`open`, `close`, `openNext`, a filter change) goes through `guarded` and sets `fix.leaving`; `keepFix` or `discardFix` answers it.
- **Other callers.** The Ledger, the Armory, the request view and a test case's + Finding call `newRecord` with `requestIds` or `testCaseId`. Create a record only through it: a record written first is visible before the tester saves.
- **Delete** awaits the store's `deleteRecord(kind, id)`. Only on success does the record leave the list and the workspace go back to it; a failure keeps it open and the page shows the error toast. Deleting a test case clears it from the findings that named it.
- **Saving through the service.** A new record is drafted as the Go bindings did (`POST /finding` with "Draft Finding", then `POST /finding/{id}/traffic {id}` per request), then Save writes the fields. A finding's save sends `cvss_vector` without `cvss_score`: the service works the score out, and refuses a score that disagrees. Artifacts upload as raw bytes with `?filename=`. `editRecord` rereads the one record (`reload`) before Edit.

## Changes made elsewhere

Another client's writes (the CLI, a phone, another app) arrive as `finding.*`, `test-case.*` and `artifact.*` events. `stores/logbookEvents.js` maps them to the store's `applyRecord`, `applyDeleted`, `applyLink`, `applyArtifact` and `applyArtifactRemoved`. The lists change in place, so the outline, filters, summary, record view, export review and Home's counts follow. Created and updated events carry no links or artifacts, so the listed record keeps its own. Tests: `logbookEvents.test.js`.

Bulk link, unlink and delete (any client's Ledger or Launchpad, or `marasi traffic bulk`) publish only `traffic.changed`, which `applyTrafficChanged` follows. A link or unlink names its finding or test case in `target`, which the store reads again (`getFinding`, `getTestCase`) once `TRAFFIC_SETTLE_MS` passes without another, so a burst reads each record once. A delete by `ids` drops those pairs from every record's links in place; a delete by query rereads every record with links. Each goes through `followed`, as below, so Requests evidence, completeness and menu checkmarks follow while an edit keeps its input. Tests: `logbookTrafficChanged.test.js`.

Reads and local changes share one clock (`touch`, `reread`, `mergedRead`). Every change applied here (an event, a delete by `ids`, this app's own write) stamps its record. A reread or `populate` applies a record's snapshot only when no change and no newer read touched that record after the read started. A change asks for a fresh read (`markStale`); a newer read replaces the older one. A deletion (`applyDeleted`, `deleteRecord`) also stamps a tombstone, so a record missing here is deleted only when its tombstone is newer than the read; otherwise it is not loaded yet, and either read adds it. Tests: `logbookStaleReads.test.js`, `logbookInitialPopulate.test.js`.

- **The modal's session** (`followed`, `rebased` in `createLogbookStore.js`): a three-way merge. The session's original becomes the new record. Each field and link the draft left as it was follows, and the researcher's input stays. When the change touched input, `session.remote` is `"changed"` and the footer says "Changed elsewhere. Save keeps yours: …". A deletion turns the session into a new record with the draft (`recreated`, `remote: "deleted"`, uploaded artifacts dropped), and Save creates it again. A session that is saving, or a new one, is left alone, so the echo of this app's own writes never raises a notice.
- **An inline fix with input** keeps it. A change to its item sets `fix.remote = "changed"` ("Changed elsewhere. Save keeps yours."), and `saveFix` already lays only the item over the current record. When its record is deleted, the input moves to the modal as a recreated session, and the Logbook page opens the modal (`showMovedSession`).
- **This app's own Delete** marks the id in `deleting` until the call returns, so its own `*.deleted` event is not taken for another client's.

## Export

`ExportReview` calls the store's `exportReport(template, reportMetadata)`. `reportBody` (`logbookApi.js`) sends `POST /report` with `start`/`end` as `YYYY-MM-DD` and `custom_properties.include_test_cases` as the top-level `include_test_cases`; the service then lists no test cases. `ReportReview` shows `reportOf(state, { includeTestCases })`. The rendered bytes go to `SaveFileAs`, named by `reportFilename` (the title plus the template's extension). Templates list and restore through `listTemplates` and `restoreDefaultTemplate`. While the review is open, `report.template.added`, `.removed` and `.restored` replace its list from the payload (`reportTemplateEvents`), and the chosen template stays while it is listed (`keptTemplate`). A gap click closes the modal and calls `open(kind, id, focus)`. The Save dialog can't be driven by an agent (a `-tags server` build has none); test the body in `logbookApi.test.js`.

## Adding a page action

1. Add a catalog row in the `logbook` block of `catalog.js`, and test its key in `menus.test.js` (see `keybindings-and-menus.md`). Esc and other reserved keys cannot be bindings, so Esc (back to the list) stays in the page's `onWindowKeydown`.
2. Add `{actionId, icon, handler}` to `logbookMenu`. `gate.js` already blocks menu actions while a modal is open; a handler that is also a button's click checks `$modalStore[0]` (or calls a helper such as `newRecord` that does). For anything that leaves the open record, it checks `fix.leaving` or goes through the store's `guard`.
3. If the action needs new state, add a store method, map its API in `logbookStore.js`, and add it to the fake API in the store tests.
