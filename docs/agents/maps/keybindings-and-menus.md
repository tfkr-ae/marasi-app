# Keybindings and menus

How a keyboard shortcut or a ⌘K menu item reaches its handler, and where a new action must be registered. Names are functions, constants and files in `frontend/src/lib/keybindings/` unless a path says otherwise, so search for them.

## How a key reaches a handler

1. **Catalog.** `FACTORY_ACTIONS` in `catalog.js` holds every built-in action. `buildCatalog` adds the extension actions. Page and drawer ids are `<context>.<slug>` (`pageActions`).
2. **Contexts.** `CONTEXTS` in `contexts.js` says when each context applies (`isEligible`) and how specific it is (tier). They read the state that `shortcutState` in `frontend/src/routes/+layout.svelte` builds. The Armory page has its own drawer, so it reports it through `armoryDrawer` in `app.js`, and the `armory.page` and `armory.drawer` contexts read `state.armoryDrawer`.
3. **Dispatcher.** `installMenuShortcuts` in `app.js` sends each keydown to `menuDispatcher` (`createDispatcher` in `dispatcher.js`). `shortcutGate` in `gate.js` first decides whether shortcuts may run, for example while a modal is open. The most specific eligible context with a live handler for the key wins. With the Marasi menu open (`"menu-open"`), every shortcut still works: `dispatch` closes the menu (`closeMenu`) and runs the action, and the menu shortcut toggles the menu. Only a key no action takes reaches the menu's own keydown handler.
4. **Handlers.** A page registers `{actionId, handler}` with `useMenuActions` for its whole lifetime. Contexts, not registrations, decide which action a key reaches. `GlobalMenu.svelte` holds the handlers and icons for `global.*`. The `global` context is eligible in every state, so a `global.*` action, such as `global.connections`, runs in every menu context unless a more specific context binds the same key.
5. **⌘K.** ⌘K opens `MarasiMenu.svelte` (in `lib/components/MarasiMenu/`). `GlobalMenu.svelte` mounts the global-tier one (Home, Settings) and publishes the catalog's `global` entries, with icons and live names, as `globalMenuEntries` (`app.js`). Every `MarasiMenu` lists them in its Marasi section. Every page with its own menu (Ledger, Launchpad, Checkpoint, Armory, Logbook, Compass, Workshop, extension pages) mounts a page-tier `MarasiMenu` with `pageName` and its menu array as `pageEntries`, which come first under the page's heading. The WebSocket modal mounts an overlay-tier one (`pageName="WebSocket"`). An extension menu item that declares no action is listed by its name and runs nothing. `MarasiMenu` draws `menuModel.js`, a pure module (`node --test`): `buildMenu` builds the sections, menu groups, loose actions and every entry's menu key from the catalog, the entries, the live keymap (`bindingsFor`) and the platform; `entryForKey` picks the entry a ⌘ key opens or runs at a level; `searchMenu` gives a search's matches in draw order. It runs actions through `menuDispatcher.run`.

## Menu groups and menu letters

- A menu group is defined in `FACTORY_MENU_GROUPS` (`menuGroups.js`): context, id, label, factory menu letter, icon (a lucide name) and tone, and a description. A menu action joins one through its `group` field (the `{ group }` option of `action` in `catalog.js`, or the `group` flag on a `pageActions` row; extension navigation actions join Go to). `menuGroupId` (`menuGroups.js`) gives a group's id, `<context>.<group>`. The catalog exposes them as `groups`, `group(context, id)` and `groupsIn(context)`, and refuses an action whose group isn't in its context. Never rename a group id.
- `RESERVED_MENU_LETTERS` (K, Q, H) sits beside the factory letters in `menuGroups.js`. Change both there.
- `groupStyle.js` maps a group's icon and tone names to the lucide component and Tailwind classes.
- A menu key is primary + the group's menu letter; an action's own first primary binding (Shift and Alt kept); else primary + a letter derived from the label's distinctive words. The menu shortcut and primary + a reserved letter are never menu keys. Menu keys are off while the search has text. A group with one action in the entries is shown as that action.
- The global groups' letters (G, P, B, A) are at the top level of every page's menu, so no page group may use them. Page groups: the Ledger (Navigate, Focus, Send to, Logbook, Copy and View with the drawer open; Focus with it closed), the Launchpad (Launch, Navigate, Compare, View, and Entries for the `launchpad.tree` actions), the Armory page (Templates, Runs) and the Checkpoint (Held items under I, since H is reserved; Rules). Logbook, Compass, Workshop, the Armory drawer, the WebSocket contexts and extension pages have no groups; their actions are loose, and one without a ⌘ binding (the Logbook's bare N) gets a derived menu letter.
- A profile can override a group's letter: `letters` in the profile (`[{group, letter}]`, group id `<context>.<group>`, the same on both platforms), next to the binding overrides. `validateLetters` in `profiles.js` refuses a non-letter, K, Q or H, and two groups at one menu level sharing a letter (`menuLevels`: the global groups, plus a context's groups and those of the contexts it conflicts with by `contextsConflict`, such as `launchpad.tree` beside `launchpad`, the same levels `catalog.test.js` checks for the factory letters), naming both groups. A letter problem never drops a saved profile on load: `liveKeybindings` hands the active profile's usable letters to the dispatcher (the saved letter wins, and `buildMenu` gives a clashing factory group a derived key), and Go's load path checks only the group ids, whose snapshot carries them as `letters`, and `MarasiMenu.svelte` passes them to `buildMenu`. `setGroupLetter`, `resetGroupLetter` and `resetGroupLetters` in `settings.js` edit them in the draft.
- `catalog.test.js` checks each group exists in its action's context, letters are unique per level (a context's groups, those of the same-tier contexts it overlaps, such as `launchpad.tree` beside `launchpad`, and the global ones), none is K, Q or H, no page group uses a global group's letter, and every group has a label, icon, tone and description.

## Adding an action

1. Add a row in `FACTORY_ACTIONS`, in its context's `pageActions` block. Never rename an existing id, because saved profiles key their overrides by it. Give every built-in action a default key: the factory profile must have no unbound action (`settings.test.js`). Unmodified Escape, Tab and Enter are reserved (`isReservedBinding`), so a page handles them itself, as the Ledger and Logbook do with Esc. A bare key, such as the Logbook's N, is allowed; it never runs while focus is in a field or editor.
2. A new context also needs an entry in `CONTEXTS`, and a field in `shortcutState` if its eligibility needs new UI state.
3. For a global action, set its menu group with `action`'s `{ group }` option (or leave it loose). Add `{actionId, icon, handler}` to the page's menu array, which it passes to both `useMenuActions` and its menu (`MarasiMenu`). A page action joins a menu group with the `group` flag on its `pageActions` row. For `global.*`, add to the `handlers` and `icons` maps in `GlobalMenu.svelte`.
4. If a row menu or the Ledger drawer rail shows the action, give the item the same `actionId`. See `ledger.md` and `launchpad.md`.
5. If the action opens a modal, pass `toggleAction: "<actionId>"` to `modalStore.trigger`, so the same key closes it (`overlayIsolation.js`).
6. Test the key in `menus.test.js`. It also catches two actions in one context sharing a key.

No test checks a handler's or a menu item's `actionId` against the catalog. A misspelt id fails silently: the menu shows no key, and the shortcut does nothing.

## Profiles and Go

- The settings UI is `frontend/src/lib/components/Keybindings/KeybindingsModal.svelte`, modelled by `settings.js`. It lists every catalog action and menu group, so a new one needs no change there. Each sidebar entry's `browse()` group carries `menuGroups` (its context's groups; the Global entry's are headed Marasi), drawn by `MenuGroupRows.svelte` above the actions, with letter conflicts worded per row and counted with the binding conflicts. `captureLetter` records one letter, not a chord. The toolbar's Reset is `resetProfile`: the platform's bindings and the profile's letters.
- `SaveKeybindings` in `keybindings.go` receives the profile with the catalog (`catalogDescriptor` in `profiles.js`: actions, contexts and menu groups with their factory letters). Go owns no list of actions or groups.
- `keybinding_validation.go` repeats the rules of `keys.js`, `gate.js`, `keymap.js` and `profiles.js` by hand (see its header). Change a rule in both. Its letter checks: the group-id check in `checkKeybindingStructure`, and `letterProblems` (bad, reserved or repeated letters through `menuLetterProblem`, then clashes per `menuLevels`), which runs only on save, worded as `validateLetters` words them; `reservedMenuLetters` repeats `RESERVED_MENU_LETTERS`.
- A saved profile reaches the dispatcher through `readKeybindings` in `frontend/src/stores.js`, then `keybindingState`, then `menuDispatcher.configure` in `GlobalMenu.svelte`.
