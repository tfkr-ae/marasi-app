# The marasi service

How the app reaches the Marasi library, how Go and the frontend talk (bindings, events, errors), and where app and project settings live. Names are functions, types and files, so search for them.

## Moving onto the service

The app is moving from the in-process Marasi library to a Marasi service instance it reaches through the control API (`.scratch/service-implementation/spec.md`). Home runs on the service; the other pages still call the bindings below until their tickets move them. Startup no longer opens a project or starts a listener in process.

- **Local instance (Go, `local_instance.go`).** `ConnectLocal` finds `marasi` on PATH (`findCLI`), runs `service status --json`, and either starts the `default` instance (`service start --port 0 --control-address 127.0.0.1:0`, a generated password in `MARASI_PASSWORD`, never in the arguments) or attaches, turning a control listener on with `service control start` when it has none. It reads the address and password back from `service control pair` over the socket, and returns `LocalConnection {url, password, instance, startedByApp}`. `ServiceShutdown` stops the instance only when the app started it (`stopOwnedLocal`). Every call goes through `runCLI`, `findCLI` and `newPassword`, which tests replace (`app_local_instance_test.go`'s `fakeCLI`), passes `--config-dir` from `MARASI_APP_CLI_CONFIG_DIR` when set, and drops inherited `MARASI_*` variables. Failures carry the `cli_missing` or `instance_failed` code.
- **Service client (`frontend/src/lib/service/`).** `client.js`'s `createServiceClient({fetch, EventSource})` is the only code that calls `fetch` for the service: `use({url, password})`, `get`/`post`/`put`/`del`/`request`, `on(eventName, handler)` (returns its unsubscribe), `openEvents({onOpen, onDrop})` and `closeEvents()`. It sends `Authorization: Bearer` unless the connection has no password. `errors.js` turns a refusal into a `ServiceError` whose text is `"<METHOD> <path>: <code>[ (<ids>)]: <message>"`, so `codeIDs` and its helpers read it; its `renames` table maps service codes the app knew by another name (`project_already_open` → `project_locked`, a 404 on a Checkpoint forward or drop → `checkpoint_gone (<id>)`, a 404 on a launchpad unlink → `not_linked`). A non-JSON refusal is `http_error` with `status`. `sse.js` is the production EventSource: a fetch-stream reader, since a native `EventSource` can't send the password. `index.js` exports the app's client, `service`. Tests: `client.test.js`, `sse.test.js`.
- **Connection store (`stores/createConnectionStore.js`, bound in `connectionStore.js`).** A pure `reduce(state, action)` returns `{state, steps, refusal}`, and the store performs the steps through its `api` (Go's `ConnectLocal`, the service client, `loadProject`, `resyncProject`, `ConfirmProjectSwitch` and `projectStore.reload`) and its `timers`. Phases: `idle`, `starting`, `connecting`, `connected`, `failed` (Retry begins again), `reconnecting` and `project-changed`. A new phase or event is a case in `reduce`, a step in `perform`, and a scenario in `connectionStore.test.js`. The password passes through steps and never sits in the state.
- **Reconnect.** A dropped `/events` (a network failure, a restart, or the service dropping a subscriber whose queue overflowed, which looks the same) is `STREAM_DROPPED`: `reconnecting`, `attempt` + 1, and a `wait` of `backoff(attempt)` (1 s doubling to 30 s). The wait's end or `retryNow()` (the banner's Retry now) is `RECONNECT_NOW`, which reaches the local instance through `ConnectLocal` again (its control address can change) and reads `/service/status`; a failure is another drop. `RECONNECTED` compares the status with `state.project` (kept current by `PROJECT_LOADED`, which `connectionStore.js` dispatches from `loadedProject`) and `state.version`, and with a `service.restarting` seen before the drop (`SERVICE_RESTARTING`), since the status has no boot id (decisions ruling 2). The same project resyncs every store in place (`resyncProject`); otherwise `project-changed` asks `ConfirmProjectSwitch`, and on yes opens `/events` and runs `projectStore.reload(path)`, the full load that remounts the pages. On no, the pages stay and the banner offers `Load it` (`loadPending()`). `ConnectionBanner.svelte` (over the page in `+layout.svelte`) shows the banner, and `lib/connectionToasts.js` the drop and reconnect toasts. Deliberate reconnects (password rotation, sharing) come with ticket 13 (ruling 3).
- **Start Chrome (`chrome.go`, `frontend/src/lib/startChrome.js`).** The frontend reads `GET /listener/status` and `GET /certificate` through the service client and hands Go's `StartBrowser` a `ChromeStart {profile, connectionKind, connectionURL, proxyListener, spkiHash}`. Go aims Chrome at that listener (a wildcard bind becomes `127.0.0.1` on the local connection and the connection's host on a remote), pins the SPKI hash, and starts it through `launchChrome` (the Marasi library's launcher; tests replace it). Paths and profiles stay in this machine's `marasi_config.yaml` through `App.chrome`, whatever the connection. Refusals carry `listener_inactive` or, on a remote whose listener binds loopback only, `listener_loopback`; `chromeErrorText` turns them into the toast. The service's `/chrome/*` routes are never called.
- **Startup.** `StartupRoutine2` (`+layout.svelte`) runs `readConfig`, then `connectionStore.start()`. On `connected`, the store opens `/events` and loads the service's project through `loadProject` in `stores/projectStore.js`, then `projectStore.loaded(path)` names it and sets `loadedProject`. Opening and switching projects is `projectStore` (see `project-open.md`).

### Adding a store to the service client

Each page ticket moves its store the same way, as `homeStore` did:

1. **The adapter, `stores/xApi.js`:** `createXApi(client)` returns the `api` object `createXStore(api)` already takes. Each method calls `client.get/post/…` and maps the API's snake_case shapes to the shape the store reads (PascalCase today), so store logic and components barely change. Logic the Go binding did on top of Marasi (paging past 500, exclusions, empty note = delete) goes here or in a small pure helper beside it. Export the mappers stream events need too (`homeApi.js`'s `toLog`).
2. **The store, `stores/xStore.js`:** `export const xStore = createXStore(createXApi(service))`, importing `service` from `lib/service/index.js`, never a binding for service data. Route its events here: `service.on("log.added", homeStore.onLog)`, with the event name from `api.md`. Handlers get the event's parsed data as the service sends it.
3. **Load and resync:** register the store once, in its `xStore.js`, with `projectData` (`stores/projectData.js`): `projectData.register("x", {signal, clear, load, resync})`. `signal` is the opening screen's part (`loadSignals` in `lib/openProgress.js`), `clear` forgets the last project, `load` is its `populate()`, and `resync` reloads server data in place, keeping what only the app holds (drafts, selection, scroll, an open drawer); leave it out when the store holds nothing local, and `load` stands in. `loadProject` (`stores/projectStore.js`) clears and loads every registered store after a switch; `resyncProject` runs every `resync` after a reconnect to the same project. Remove the store's line from `resetProject` in `stores.js`. The store's module must be imported before the first load: `stores.js` imports the page stores today, and `projectStore.js` imports `homeStore.js`.
4. **Tests:** run `createXStore(createXApi(fakeClient))` with a fake client whose `get`/`post` answer from a route table, as `homeStore.test.js` does, so the mapping and the store are tested together through their public surface. Keep the store's existing fake-api suites. Add a `resync()` test proving it replaces server data and keeps the local state (Home's: the old counts stay until the new arrive).
5. **Errors:** a refusal the page acts on is read with `codeIDs` as before. If the app knew it by another code, add a row to `renames` in `lib/service/errors.js` with a case in `client.test.js`.
6. **Wails events:** remove the page's `on`/`off` for the old Wails event in `+layout.svelte`.

## Marasi source

The app pins `github.com/tfkr-ae/marasi` in `go.mod`. `GOWORK=off go list -m -f '{{.Dir}}' github.com/tfkr-ae/marasi` gives that version's source. `~/Projects/marasi-project/marasi` is the sibling checkout, for unreleased changes.

## What the app holds

`App.Proxy` is the `*marasi.Proxy`. Its repositories are nil until a project opens, so call the checked getters (`GetTrafficRepo`, `GetConfigRepo` and the rest), which return an error instead. `App.projects` is marasi's `service.ProjectLifecycle` (open, shut down, background jobs), `App.listener` is the proxy listener, `App.chrome` reads and writes this machine's Chrome paths and profiles, and `App.upstreamProxies` is marasi's `service.UpstreamProxies`. `newApp` sets all five. `NewApp` builds the proxy, and tests pass their own.

## Bindings

`main` registers `App` as the Wails v3 application's only service, so every exported `App` method in package `main` is callable from the frontend, whatever file it is in (`ServiceStartup` and `ServiceShutdown` are not). `wails3 generate bindings -d frontend/src/lib/bindings` generates JavaScript from them; frontend files import the calls from `frontend/src/lib/bindings/github.com/tfkr-ae/marasi-app/app.js`. That directory is gitignored and wiped on each run, so regenerate it (or run `scripts/bootstrap.sh`) after you add a method or change its signature. Run `wails3` with `GOWORK=off`, at the version `go.mod` pins.

A binding returns Go structs as instances of generated model classes, with the fields encoding/json gives them: a struct without json tags reaches JS with PascalCase field names. A field missing from the JSON gets its zero value, and a nil slice or map arrives as `[]` or `{}`. A Go error rejects the promise with a `RuntimeError` whose message is the `Error()` text. `runtime.js` makes a `RuntimeError` read as its message alone, so `String(err)` and template strings show the bare text, as in v2.

To add a call: write the `App` method in its topic's file and test it with a project open (`newProjectApp`). Then regenerate the bindings, call the method from the topic's `stores/xStore.js`, and keep the logic in `stores/createXStore.js`, which takes its API as an argument so `node --test` can run it.

## Desktop seams

`App` reaches the desktop runtime only through replaceable functions, which `useDesktopRuntime` in `desktop.go` points at the Wails application in `App.wails` (set by `main`, nil in tests). Nothing else calls Wails, so tests replace these, and a Wails upgrade changes only that file. Their option types (`messageDialogOptions`, `openDialogOptions`, `saveDialogOptions`, `fileFilter`) are the app's own, in `dialog.go`.

- `emitEvent` sends an event, and `onEvent` listens for one from the frontend and hands over its payload.
- `messageDialog` shows a message dialog and returns the pressed button's label. `showMessageDialog` waits for the pressed button's callback, and doesn't attach the dialog to the window, because a macOS sheet returns before the click. A `-tags server` build has no dialogs (`serverBuild`), so it answers the cancel button. `nativeMessageDialog` (`dialog.go`) adapts confirmations for Windows and Linux.
- `openFileDialog` and `saveFileDialog` return the chosen path, or `""` when the user cancelled. `fileDialogResult` turns Windows' "cancelled by user" error into `""`. Callers treat `""` as a cancel and do nothing.
- `setClipboardText` puts text on the clipboard.
- `quitApp` calls the Wails application's `Quit`, which asks `shouldQuit` (the `ShouldQuit` option) on every OS, then runs `ServiceShutdown`.

**Quitting and closing.** `shouldQuit` runs on the main thread, so it never shows a dialog: it lets a quit go ahead when it is confirmed or would lose nothing, and otherwise refuses and asks in the background (`askThenQuit`), quitting again on a yes. The window's `WindowClosing` hook (`main.go`) calls `windowClosing`, which cancels the close and asks and quits the same way, so every OS shuts down through `Quit` (Wails issue #6368 skips shutdown when Windows closes the last window). `beforeClose` asks about unsaved work once per quit: after a confirmed quit or "Restart now", it lets Marasi close without asking again, and the quit's own closing of the window goes ahead. `askingToQuit` keeps it to one prompt at a time. `ServiceShutdown` calls `relaunchIfRestarting` last.

**The window and menu.** `main.go` opens one window (Marasi, 1600×900, background RGB 27, 38, 54). On macOS, `applicationMenu` (`menu.go`) sets only the app and Edit menus, so Wails' default View and Window shortcuts don't fire over Marasi's. On Windows, `handleWailsError` (`wails_error_windows.go`) says so when the WebView2 runtime is missing, since the exe ships without an installer. The app sets no WebView2 resource filter (Wails issue #6530).

## Errors the frontend acts on

The frontend can only match error text, so an error it must act on carries a code: `<what>: <code>: <cause>`, or `<what>: <code> (<id>, <id>): <cause>` when it names items. Go builds them with `codedError`, `launchpadError` and `openProjectError`. `codeIDs` in `frontend/src/lib/errorCodes.js` reads them back, and helpers such as `launchPending.js` build on it. To handle a new Marasi refusal, add a code constant with a doc comment, wrap the error with `codedError`, then add a frontend helper that calls `codeIDs`.

## Events

- **Go to frontend.** Every event goes through `a.emitEvent`, which tests replace (`recordedEvents`), including Marasi's request, response and log events (`configureTrafficHandlers`) and the `log` events of the logger `ServiceStartup` attaches (`LogHandler`). Register Marasi handlers in a `configure*Handlers` function called from `newApp`, not in `ServiceStartup`: each Marasi `With*Handler` option fails when its handler is already set.
- **The frontend's runtime module.** `frontend/src/lib/runtime.js` is the only frontend file that calls the Wails runtime (`@wailsio/runtime`, pinned to the Go module's version) for anything that isn't a binding: `on`, `once`, `off`, `emit`, `setWindowTitle` and `openURL`. Wails hands a listener a `{name, data}` event; a subscriber's callback receives `data`, the payload: the value Go emitted, or `null` when it sent none. `on` and `once` return a function that removes that one listener, and `off` removes every listener for a name. Import from it, never from `@wailsio/runtime`. `runtime.test.js` runs it against a fake runtime.
- **Frontend subscriptions** are in `onMount` in `frontend/src/routes/+layout.svelte`, which forwards each event to a store's `on*` method. Add the matching `off` to its cleanup.
- **Two shapes on `log`.** Marasi's stored logs (`domain.Log`) have capitalised fields. The app's own records (`LogHandler`, and the project lifecycle's log through `newRelayLogger`) have lowercase ones. The Home log table (`LogTable.svelte`) reads `Level`.
- **Frontend to Go.** Extension UIs send `extension_call_function` and `extension_sync_state`. `LoadExtensions` listens for them through `a.onEvent` (the Wails event's `Data`), and `decodeExtensionFunctionCall` and `decodeExtensionSync` read their payloads.

## Settings

- **App settings** are in `marasi_appconfig.yaml` in the config directory (`Config`, `LoadConfig` in `config.go`). Exported `Config` fields reach the frontend through `GetMarasiConfig`. Flags in `configDefaults` change through `ToggleFlag` and `SetFlag`. Other sections each have a key constant, a `parse*` function called from `LoadConfig`, and getters and setters that write through `writeConfigKeys` in `config_file.go`.
- **Per-project settings** are client settings in the project file, under the client `appClient` (`client_settings.go`). Stores call the generic bindings with their own key prefixes. A key that both Go and JS use is written out in both.
- **App default with a project override.** `content_type_exclusion.go` is the pattern, from [Ledger settings are app defaults with project overrides, stored by the app](../../adr/2026-10-16-app-defaults-with-project-overrides.md).
- `marasi_config.yaml` is Marasi's own config, which service instances share. The app does not keep its settings there.
- **Upstream proxies** (`upstream_proxy.go`). The list is in `marasi_config.yaml` and the selection is a project setting under Marasi's reserved client, so both go through `service.UpstreamProxies`, the same methods the control API handlers call. Its edits take the config lock that every instance shares. It sends the app no events, so Settings reads the list again each time the section opens. Opening a project applies that project's selection, through `ProjectLifecycle`. A selection this machine doesn't list fails the project's traffic closed, and `UpstreamProxyState.configured` reports it.
