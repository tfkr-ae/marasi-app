# The marasi service

How the app reaches a Marasi service instance (the bindings, the Marasi client module, events, errors), what the main process holds, and where app and project settings live. Names are functions, types and files, so search for them.

## Marasi source

The bundled Marasi is built from the commit `package.json`'s `marasi` key pins (`scripts/build-marasi.sh`). `~/Projects/marasi-project/marasi` is the sibling checkout; its `integration/v2-backlog` branch has the control API routes and events the app calls.

## What the app holds

The renderer holds no Marasi state of its own: each store reads the connected instance and follows its events. The main process (`electron/main.js`) holds each window's connection by webContents id, `{instance, origin, token, loopbackTurnedOn, remote}`: `createLocalConnections` in `electron/local.js` connects to, starts and stops local instances through their sockets (`electron/instances.js`, `electron/socket.js`), and `createRemotes` in `electron/remotes.js` holds remote ones. `withBearer` (`electron/bearer.js`) adds the window's token to its requests, so the page never holds it. `createWindowList` (`electron/windows.js`) tracks the windows, and the preload (`electron/preload.mjs`) is the renderer's `window.marasiApp`. In a plain browser `frontend/src/lib/bindings/browserBridge.js` stands in for it, with the dev server (`frontend/devBridge.js`) answering for the main process.

## Bindings

Pages call v1's binding names from `frontend/src/lib/bindings/App.js`, which ports each one onto the Marasi client module or the main process; one that isn't ported rejects with `NotPorted` (`notPorted.js`). Bindings answer in v1's shapes (PascalCase fields), and topic helpers turn Marasi's JSON into them (`traffic.js`, `launchpads.js`, `armory.js`, `records.js`, `websocket.js`, `reports.js`). `appConfig.js`, `chrome.js`, `extensions.js`, `updates.js` and `runtime.js` (v1's Wails runtime) are the other binding modules. `docs/v2-parity.md` lists every binding, and `parity.test.js` checks it.

The Marasi client module, `marasi` in `bindings/marasi.js`, calls the window's connection: `get`, `post`, `put`, `delete`, and `sendBytes`, `readBytes` and `postBytes` for bodies that aren't JSON. `useConnection` points it at a connection's origin; the window connection store (`stores/windowConnectionStore.js`) calls it.

To add a call: write the binding in `App.js` on `marasi`, test it against a fake `fetch` in the topic's `*Bindings.test.js`, call it from the topic's `stores/xStore.js`, and keep the logic in `stores/createXStore.js`, which takes its API as an argument so `node --test` can run it.

## Errors the frontend acts on

Marasi refuses with `{error: "<code>", message?, …}`. `MarasiError` in `bindings/marasi.js` turns it into text the code helpers read: `<method> <path>: <code>: <message>`, or `<method> <path>: <code> (<id>, <id>): <message>` when the refusal names ids. A route the instance doesn't have rejects with `NeedsNewerMarasi` ("Needs a newer Marasi"). `codeIDs` in `frontend/src/lib/errorCodes.js` reads a code and its ids back, and helpers such as `launchPending.js` build on it. To handle a new Marasi refusal, add a helper that calls `codeIDs` with its code.

## Events

- **Marasi to the stores.** `frontend/src/lib/marasiEvents.js` follows the window connection's `/events` (`createEventStream` in `eventStream.js`, kept on the current connection by `followConnection.js`) and sends each event to a store's `on*` method through its `handlers` row. Wrap a store's re-read in `logged()` so a failure is logged. Every store that shows instance data is in `stores`, whose `reload()` runs after the stream reopens, as Marasi doesn't replay events.
- **Main process to the renderer.** The updater's events reach `EventsOn` in `bindings/runtime.js` through the preload's `onUpdateEvent`; no other name arrives there.
- **Logs.** `stores/createLogStore.js` reads `GET /logs` and follows `log.added`; `LogTable.svelte` shows them.
- **Extensions in v2.** `stores/createExtensionsStore.js` follows `extension.enabled`, `extension.updated`, `extension.settings.updated`, `extension.gui.rendered`, `extension.gui.updated` and `extension.log` (wired in `lib/marasiEvents.js`). It is `extensions` and `extensions_ui` in `stores.js`. A `toast` render goes to the layout's toasts, and log lines go to `ExtensionLogs.svelte`'s followers. Buttons and v1's `extension_sync_state` call `POST /extension/{id}/call` (`callExtensionFunction` in `lib/extensions/components/utils.js`), passing the extension's UI as the one argument, as v1 did. Marasi doesn't replay renders, so a reloaded page shows an extension's UI only after it draws again. Settings → Extensions (`ExtensionsSettings.svelte`) turns extensions on or off and edits their settings.
- **Scope in v2.** `stores/createScopeStore.js` reads `GET /scope` on project open and again on `extension.updated` for compass, as Marasi has no scope event. Compass's rule list (`ScopeRules.svelte`) and the dashboard's scope cards read it.

## Settings

- **App settings** are in `marasi_appconfig.yaml` in the config directory, which v1 and v2 share. In v2 the main process owns it: `electron/appConfig.js` (flags, highlights, app saved queries, the default exclusion, test cases) and `electron/keybindings.js` read the file on every call and write one key at a time through `electron/configFile.js`, which keeps unknown keys. The renderer reaches them through `marasiApp.appConfig` (`electron/appConfigIPC.js`, the preload) and the bindings in `frontend/src/lib/bindings/appConfig.js`, which check keybindings against the catalog and normalise the exclusion before they send. v1's version was `Config`/`LoadConfig` in `config.go` and `writeConfigKeys` in `config_file.go` on `main`.
- **Per-project settings** are client settings in the project file, under the client `marasi-app` (`/client-settings/marasi-app` in `App.js`). Stores call the generic bindings (`GetClientSetting`, `SetClientSetting`, `ListClientSettings`, `DeleteClientSetting`) with their own key prefixes.
- **v2-only app config keys** start with `v2_` (`v2Value`, `setV2Value` and `updateV2Value` in `electron/appConfig.js`), so v1 never reads them: the updater's settings, `v2_remote_connections`, and the Chrome keys below.
- **App default with a project override.** The Ledger's exclusion is the pattern (`GetContentTypeExclusion` in `App.js`: `ledger.exclusion`, else the app default), from [Ledger settings are app defaults with project overrides, stored by the app](../../adr/2026-10-16-app-defaults-with-project-overrides.md).
- `marasi_config.yaml` is Marasi's own config, which service instances share. The app does not keep its settings there.
- **Upstream proxies.** The list is in `marasi_config.yaml` and the selection is a project setting under Marasi's reserved client. In v2 the bindings in `frontend/src/lib/bindings/App.js` call `/upstream-proxy*`; Marasi answers add, update and remove with the list alone, so those bindings read `GET /upstream-proxy` after the change to answer v1's whole state with the selection. `ReadUpstreamProxyCAFile` reads a PEM on this machine (`electron/caFile.js`, or `MARASI_UPSTREAM_PROXY_CA_FILE` in place of the dialog; a file input in the browser bridge). `createUpstreamProxyStore.js` follows `upstream_proxy.*`, so a change from the CLI or another window shows up live, and a selection this machine doesn't list shows as not set up, as Marasi fails its traffic closed. v1's Go side was `upstream_proxy.go` on `main`.
- **Chrome and waypoints.** `createChromeStore.js` holds the instance's Chrome paths and profiles (Settings → Browser, Home's Start Chrome menu) and follows `chrome.*`; `createWaypointStore.js` holds the open project's waypoints and follows `waypoint.*`. On a local connection the Chrome bindings call `/chrome/*`, and Start Chrome opens Chrome on the instance's machine through its proxy listener. On a remote connection Chrome is this machine's (`frontend/src/lib/bindings/chrome.js`, `electron/localChrome.js` behind `localChromeIPC.js`): the app's own paths and profiles in app config keys `v2_chrome_paths` and `v2_chrome_profiles`, user-data-dirs in `<config dir>/v2_chrome_profiles/`, and Marasi's switches. Start Chrome reads `GET /listener/status` and `GET /certificate`'s `spki_hash`, then points Chrome at the remote's proxy address: the one Settings → Browser saved for that remote in `v2_chrome_proxy_addresses` (keyed by the window's own connection origin in the main process), or else the connection's host with the listener's port. The store ignores the instance's `chrome.*` events there.
