# The marasi service

How the app reaches a Marasi service, how Go and the frontend talk (bindings, events, errors), and where app and project settings live. Names are functions, types and files, so search for them.

## The shape

Every page works against a Marasi service instance through its control API and its `/events` stream (`.scratch/service-implementation/spec.md`). The frontend's service client makes every API call and the connection store keeps the connection; Go is a desktop shell (see "The Go shell") and never opens a project, runs a proxy or reads a repository. Startup opens no project and starts no listener in process.

## The service side

- **Local instance (Go, `local_instance.go`, `owned_runs.go`).** Every local-instance binding takes a local connection's id and reaches the instance it names (`localInstanceFor`: Local, id `local`, names `default`; a saved connection of kind `local` names its `instance` and `port`; any other id is refused before the CLI runs). `localFor(id)` keeps one `localInstance {connection, name, cliPath}` per connection id, whose mutex serializes that instance's CLI calls, and `cli` passes its `--instance`. `ConnectLocal(id)` finds the Marasi CLI (`findCLI`, see Marasi CLI below), runs `service status --json`, and either starts the instance (`service start --address <default_address> --port <default_port> --control-address 127.0.0.1:0`, retried on `127.0.0.1` when the address isn't one of this machine's (`addressMissing`, EADDRNOTAVAIL: an app config copied from another machine; the setting is kept), then once with `--port 0` when the port is taken (`portTaken`); an added local connection starts on its saved `--port`, or `--port 0` when it has none, with no retry, and with `--project-name <instance>` unless a project is given (Marasi's own pick is the scratchpad, which `default` holds open); a start creates an instance that has never run; a generated password in `MARASI_PASSWORD`, never in the arguments) or attaches, turning a control listener on with `service control start` when it has none. It reads the address and password back from `service control pair` over the socket, and returns `LocalConnection {url, password, instance, startedByApp}`. **Saved ownership (GLOSSARY Owned run):** app config's `owned_runs` maps each local connection id to the `run_id` the app last started there. Every start through the app (`startLocal`: the connect that starts the instance, and `RestartLocalInstance`) saves the new run's `run_id` from `service status` (`saveOwnedRun`); a run without one isn't saved. On every connect, `ownsRun` compares the instance's current `run_id` with the saved one: equal is owned, whether this launch or an earlier one started it, and anything else (another client restarted or replaced it, or it stopped) clears the record. `startedByApp` is that answer. When the quit's answer is Stop (see The quit question), `ServiceShutdown` runs `stopOwnedRuns`: for every connection with a saved run, it reads the status at quit and stops the instance (`service stop --instance <name>`) only while the run there still matches, so a run an earlier launch started stops too and another client's replacement keeps running; the record goes either way. The connection store's `owned` takes each local connect's `startedByApp` as it comes (`ownedAfter`), so it follows the saved ownership and a replacement too, and the Restart confirms (`OutdatedInstance`, `UpdateCLI`) ask only when it is false. Every call goes through `runCLI`, `findCLI` and `newPassword`, which tests replace (`app_local_instance_test.go`'s `fakeCLI`), passes `--config-dir` from `MARASI_APP_CLI_CONFIG_DIR` when set, and drops inherited `MARASI_*` variables. Failures carry the `cli_missing` or `instance_failed` code, or `instance_outdated` when the running instance answers a control route with 404 (an older Marasi, such as the v2 app's bundled build, without pairing); its cause names the running version. `StopLocalInstance(id)` (`local_start_stop.go`) runs `service stop` whoever started the run (one already stopped counts as stopped) and clears the owned run; `StartLocalInstance(id, project)` starts a stopped instance on `project` through `startLocal`, so the app owns the new run, and leaves a running one for `ConnectLocal` to attach to (`app_local_start_stop_test.go`). `LocalInstances()` lists the instances `service list --json` reports as `LocalInstance {instance, status, version, project, proxy_listener}` (running or unhealthy; a stopped one isn't listed). `AddConnection.svelte` lists the ones no saved local connection names (`unsavedInstances` in `lib/connection/localInstances.js`), each with an Add that saves it named for its instance on its current proxy port (`connectionFor`); a stopped or new instance is typed. `RestartLocalInstance(id)` stops that instance and starts its project again through the same start path, so the app owns the new run; `lib/connection/OutdatedInstance.svelte` offers it (with a confirm) in `ConnectionDetail` and on the startup failure screen, and `outdatedVersion` (`cli.js`) reads the version.
- **Marasi CLI (`cli.go`, `cli_config.go`, `cli_locate.go`, `cli_install.go`, `cli_archive.go`, `cli_carried*.go`; ADR `2026-11-08-the-app-carries-a-compressed-cli-it-installs-once`).** `LocateCLI` tries `cli_path` in app config, then `marasi` on PATH, and accepts a candidate only when its `service status --json` answers as Marasi does; version and channel come from the binary's Go build info (`-X main.version`/`main.buildChannel`), never by running it. `UseCLIPath` probes before saving (`cli_path_source: custom`), `ClearCLIPath` goes back to PATH, `BrowseCLIPath` is the file dialog. `InstallCLI(dir)` and `CheckForCLIUpdate` read the release on the CLI channel (`cli_channel`: absent follows the app, a dev app follows release; `SetCLIChannel("app"|"release"|"nightly")`), verify `checksums.txt.minisig` with `marasiCLIPublicKey` and a trusted comment of exactly `marasi <channel> <version>`, then the build's SHA-256, and only then copy it beside the target (emitting `cli-install-progress` `{step: download|verify|extract|install, received, total}` throughout, which `CLIProgress.svelte` shows), `chmod 0755` it (not on Windows) and rename it in, saving `cli_path_source: installed`. On Windows the target may be the running service's `marasi.exe`, so `placeCLI` installs through `swapAside` (`update_install_exe.go`, shared with the app's Windows updater): it moves the target aside to `marasi.exe.old`, renames the new build in, and moves the old one back when that fails; `ServiceStartup` removes the `.old` beside the saved and PATH CLIs (`removeCLILeftovers`, retried while its process exits). Builds: the platform's archive (`cliArchives` in `cli_archive.go`: `marasi-darwin-arm64.zip`, `marasi-linux-amd64.tar.gz`, `marasi-windows-amd64.zip`), which networks that block bare executables let through, whenever the signed `checksums.txt` lists it and the release has it; otherwise the bare executable (`cliAssets`: `marasi-darwin-arm64`, `marasi-linux-amd64`, `marasi-windows-amd64.exe`). An archive's SHA-256 is checked before `extractCLI` opens it, and it must hold exactly one regular file named `marasi` (`marasi.exe` on Windows) and nothing else, or the install fails closed. The extracted CLI goes through `placeCLI`, which places bytes from any reader, as a download does. Marasi publishes the archives beside the bare executables from its `be1ee39` on (`scripts/archive-cli.sh`, run by its Release and Nightly workflows), so a release or nightly built before that, such as `30.10.2026`, has none and takes the bare executable. Any other platform fails `no-build` before asking GitHub. The carried CLI: release and nightly builds carry their platform's CLI, gzipped. `build.yml` (which `release.yml` and `nightly.yml` call) runs `cmd/carry-cli` before it builds: it reads the latest CLI release on the app's channel, verifies `checksums.txt.minisig` with the same key (`internal/marasicli`, shared with `marasiCLIPublicKey` and `cliAssets`) and trusted comment rule, checks the SHA-256, and writes `carried_cli/marasi.gz` and its record `carried_cli/carried.json` (`version`, `channel`, `goos`, `goarch`, `sha256`; git-ignored); any failure fails the build. The `carried_cli` tag embeds them (`cli_carried_embed.go`, only on darwin/arm64, linux/amd64 and windows/amd64, so the amd64 half of the universal macOS build carries none); without it (`cli_carried_none.go`, any development build) `cliRuntime.carried` is nil and Install downloads. `InstallCLI` places the carried copy only when it is for this platform and `LocateCLI` finds no CLI (`usableCarriedCLI`), so discovery is unchanged and an existing CLI is never replaced. It makes no network request: it emits the `extract` step and streams the gzip reader through `placeCLI`, checking the SHA-256 as the last byte is read (`checkedReader`; a mismatch fails `checksum` and leaves nothing), saves `cli_path_source: installed`, reports the record's version and channel, then runs `CheckForCLIUpdate` in the background (`cliRuntime.background`, `checkForCLIUpdateAfterInstall`), which installs a newer release as Check for CLI update does and emits its result as `cli-update-checked` (`CLI_UPDATE_CHECKED_EVENT` in `cli.js`; a failure is logged and keeps the carried copy). `+layout.svelte` toasts a newer install (`cliUpdateCheckedNotice`), and `CLISettings.svelte` shows the check's progress and the CLI it left. The app never runs the carried copy where it is embedded. Tests: `cli_carried_test.go` (fake carried copy, counted network), `cli_carried_dev_test.go` (no tag, no copy), `cli_carried_embed_test.go` (with the tag and `carried_cli/`: the embedded build matches its record), `cmd/carry-cli/main_test.go` (fake releases API). Every effect goes through `App.cliRuntime`, which `cli_install_test.go`, `cli_install_archive_test.go` (archives, including the ones in `testdata/cli-archives` that Marasi's `scripts/archive-cli.sh` built), `cli_install_live_test.go` (opt-in with `MARASI_CLI_LIVE_DIST`: installs a real build and its archive, then starts an instance with it), `cli_install_exe_test.go` (Windows file locks, bare and archive) and `cli_locate_test.go` replace (fake release server, test key). Frontend: `lib/connection/cli.js` (pure), `CLISetup.svelte` (in `ConnectionDetail` on `cli_missing`; `+layout.svelte` opens the Connections modal by itself once per such failure) and `CLISettings.svelte` (Settings → Updates, its Marasi CLI part; `?section=cli` still lands there).
- **Service client (`frontend/src/lib/service/`).** `client.js`'s `createServiceClient({fetch, EventSource})` is the only code that calls `fetch` for the service: `use({url, password})`, `get`/`post`/`put`/`del`/`request`, `on(eventName, handler)` (returns its unsubscribe), `openEvents({onOpen, onDrop, onReset, resume})` and `closeEvents()`. The client keeps the last event id the stream carried (`<run_id>.<seq>`, opaque); `resume: true` reopens `GET /events?last_event_id=<id>` (an EventSource can't set `Last-Event-ID`) and the service replays what was missed, a fresh `openEvents()` forgets the id, and `closeEvents()` keeps it. A `stream.reset` reaches `onReset(reason)` (`expired`, `restarted`, `invalid`), and so does `"none"` once open when a resume had no id to send (the stream before carried no event). For the routes that aren't JSON, `request(method, path, {raw, contentType})` sends bytes (an artifact) and `{as: "bytes"}` resolves to the answer's bytes (artifact content, a report); `SaveFileAs` (`save_file.go`) saves such bytes through the native Save dialog. It sends `Authorization: Bearer` unless the connection has no password. `errors.js` turns a refusal into a `ServiceError` whose text is `"<METHOD> <path>: <code>[ (<ids>)]: <message>"`, so `codeIDs` and its helpers read it; its `renames` table maps service codes the app knew by another name (`project_already_open` → `project_locked`, a 404 on a Checkpoint forward or drop → `checkpoint_gone (<id>)`, a 404 on a launchpad unlink → `not_linked`). A non-JSON refusal is `http_error` with `status`. A call that gets no answer is `unreachable` (fetch rejected: a refused or blocked connection, which WebKit reports only as "Load failed") or `timeout` (`request`'s `timeout` ms ran out), and its text is just `Couldn't reach <host:port>` or `No answer from <host:port>` (`unreachable` in `errors.js`). `sse.js` is the production EventSource: a fetch-stream reader, since a native `EventSource` can't send the password. It reads `id:` lines into `lastEventId` as a native one does (an event without one, such as `stream.dropped`, keeps the last). Each `use()` begins a new connection generation, and `bind()` returns the calls bound to the current one (`{live(), request, get, post, put, del}`): once `use()` moves on, a bound call rejects unsent with a `superseded` ServiceError (`isSuperseded` in `errors.js`), and so does an answer landing after the move. A caller that awaits before a write binds first and treats superseded as a no-op: the project store's runs and the connection store's status and control calls. A user action of several calls (an api's `bind()` passes the client's on) runs each as a step of `boundAction(api.bind?.())` (`boundAction.js`), captured as the action starts: a step refuses to start, and an answer landing after the move rejects, once the client moved. An api call that reads then writes binds inside itself (Checkpoint's `forwardMany` and both intercept toggles, the Armory template from a request, the Logbook draft and its links, WebSocket inject and close, the waypoint save). `toastError` (`lib/toasts.js`) shows nothing for superseded, and so do the pages' own error toasts. Tests: `connectionSwitchWrites.test.js` over `switchingService.js` (the real client, switching from A to B as a chosen request answers). `index.js` exports the app's client, `service`. Tests: `client.test.js`, `sse.test.js`.
- **Connection store (`stores/createConnectionStore.js`, bound in `connectionStore.js`).** A pure `reduce(state, action)` returns `{state, steps, refusal}`, and the store performs the steps through its `api` (Go's `ConnectLocal`, the service client, `projectStore.loadService`, `resyncProject`, `ConfirmProjectSwitch` and `projectStore.reload`) and its `timers`. Phases: `idle`, `starting`, `connecting`, `connected`, `failed` (Retry begins again), `reconnecting`, `project-changed` and `stopped`. **Stop and Start:** `STOP` (only `connected`) asks first when `owned` is false or the connection is a remote, which the app can't start again (`stopAsk`, answered by `STOP {confirmed}` or `CANCEL_STOP`, as Restart asks), then sets `busy: "stop"`, closes `/events` and runs `stop-instance` (Go's `StopLocalInstance`) for a local connection or `stop-service` (`POST /service/stop` through `api.bind()`, the service's own stop route) for a remote; `INSTANCE_STOPPED` is `stopped`, with a `service-stopped` step (`api.serviceStopped()`, which `connectionStore.js` points at Home's `onListener`, so the listener chip reads Listener off: no `listener.stopped` event comes over the closed stream), `STOP_FAILED` keeps `connected` with `stopError` and resumes the stream. `stopped` names no connection kind, so a remote's stop reaches it too: the stream is closed, the pages stay dimmed and inert (`pagesHeld` in `status.js`, as in `project-changed`), `ConnectionBanner` and `ConnectionDetail` say "Marasi stopped" with Start for a local connection and Retry for a remote, and no drop, wait, reset or followed switch leaves it. `START` begins a new session with `switching` set, whose `start-local` step runs `StartLocalInstance(id, project)` on the project the pages showed and then `ConnectLocal`, so `CONNECTED` loads it in full (`reload-project`). Tests: `connectionStop.test.js`, and `connectionStopRemote.test.js` for a remote. A local connection that isn't active gets Stop (while the CLI's `LocalInstances` lists its instance) and Start in its `ConnectionDetail` through `lib/connection/instanceControl.js` (`localInstanceControl` in `manage.js` binds it to `StopLocalInstance`, `StartLocalInstance(id, "")` and `OwnsRun`): Stop asks first for a run the app doesn't own, neither touches the connection store or the active connection, and each reads the instance and its ownership again, which turns Remove on after a Stop (`instanceControl.test.js`). A new phase or event is a case in `reduce`, a step in `perform`, and a scenario in `connectionStore.test.js`. Every status read passes `STATUS_TIMEOUT_MS` (10 s), so a host that drops packets fails the connect instead of keeping it Connecting; `failed` shows its `error` in `ConnectionDetail` and, once the pages are up, in `ConnectionBanner`, each with Retry (`connectionUnreachable.test.js` runs the store over the real client). The password passes through steps and never sits in the state. Each `begin()` (start, switch, Retry, an edited address, a saved password) bumps `state.session`; every step, `/events` handler and wait runs tagged with its session and, after each await, acts only while that session is current, so a late answer from an older attempt changes nothing (`connectionAttempts.test.js`). A new async step follows the same rule: `settle(session, action)` to dispatch, `current(session)` before any other effect, and service calls through `api.bind()` taken after its own `use()`. Each new session calls `api.sessionBegan()` before its steps; `connectionServiceApi.js` (the api's service half, which the tests share) points the client at nothing and calls `projectStore.leave()`, so nothing the last session started reaches the next connection (`projectOpenSwitch.test.js`). `load-project` and `reload-project` pass `current` to the project store, so a switch supersedes their load (see `project-open.md`, "Load and pages").
- **Saved connections (`connections.go`, `keychain.go`).** `marasi_appconfig.yaml` keeps `connections` (id, name, kind, URL, `no_password`, `password_ref` for a remote; kind `local` with `instance` and `port`, 0 for any free port, for a local connection the researcher added), `active_connection`, `recent_projects` per connection id and `owned_runs` per local connection id (see Local instance); never a password. `AddConnection` (a remote), `AddLocalConnection` (a named instance not saved yet; `default` is Local's; names checked as the CLI does), `SetConnectionAddress`, `SetConnectionPort` (an added local connection), `SetConnectionPassword`, `RemoveConnection` (not Local, the active one, or a local connection whose run the app owns (`OwnsRun`): "Stop it first", since a forgotten run would outlive quit; drops its recents and a remote's password, leaving a local instance running), `SetActiveConnection`, `RecentProjects` and `AddRecentProject` are the bindings. Passwords go to the OS keychain on release builds and otherwise, or when the keychain refuses, to `marasi_app_passwords.json` (`0600`) beside the config; the ref says which (`keychain:`/`file:`). Tests: `app_connections_test.go`, `app_local_connections_test.go` (local connections, their recents and owned runs); named instances' start, stop and list are in `app_local_start_stop_test.go`. The store's `CONNECTIONS_LOADED`, `SWITCH_CONNECTION` (guarded by `ConfirmProjectSwitch`, then close `/events`, `set-active`, `clear-stores`, begin), `AUTH_REJECTED` (phase `auth-failed`, no timer) and `ENTER_PASSWORD` cover remotes (`connectionRemote.test.js`); `stores/recentProjects.js` adds each newly loaded project to the active connection's recents.
- **macOS App Transport Security.** The web view reaches every service over plain HTTP, and a remote can be any host (a Tailscale 100.x address, a LAN IP, a hostname), so both `build/darwin/Info.plist` (release and nightly, copied into the bundle by `create:app:bundle`) and `Info.dev.plist` set `NSAppTransportSecurity` with `NSAllowsArbitraryLoadsInWebContent` (exempts WKWebView loads only, not URLSession) and `NSAllowsLocalNetworking` (IP addresses and `.local` names, which macOS 14+ refuses by default). Without them only loopback works and a remote fails with `Couldn't reach …`. `build_plist_test.go` fails if either plist loses them.
- **API level.** The app supports the API levels in `SUPPORTED_API` (`lib/service/apiLevel.js`, min 1, max 1), the one place the range lives: raise `max` in the change that adopts a new level, `min` when the app drops an old one. `CONNECTED`, `RECONNECTED` and `STATUS_REFRESHED` keep the status's `api` and set `apiWarning` (`apiWarning(api)`) outside it; a status with no `api` is from a Marasi older than API levels, so too old. Never compare versions. `ConnectionBanner.svelte` and `ConnectionDetail.svelte` (which also shows the level) show the warning; it never blocks. On the local connection both offer `lib/connection/UpdateCLI.svelte`: `updateCLI` (`cli.js`) runs `CheckForCLIUpdate` (with `CLIProgress`), then `RestartLocalInstance`, asking first when `owned` is false, then `retryNow()`; the restart's new run ID loads the project in full. A remote only warns. Marasi doesn't publish its releases' API levels, so the install takes the CLI channel's latest.
- **Reconnect.** A dropped `/events` (a network failure, a restart, or the service dropping a subscriber whose queue overflowed after `stream.dropped {reason: overflow}`) is `STREAM_DROPPED`: `reconnecting`, `attempt` + 1, and a `wait` of `backoff(attempt)` (1 s doubling to 30 s). The wait's end or `retryNow()` (the banner's Retry now) is `RECONNECT_NOW`, which reaches the local instance through `ConnectLocal(id)` again (its control address can change) and reads `/service/status`; a failure is another drop. `RECONNECTED` compares the status's `run_id` with `state.runId` (a new one on every start of the service process) and its project with `state.project` (kept current by `PROJECT_LOADED`, which `connectionStore.js` dispatches from `loadedProject`). The same run and project is `connected` with `open-events` `resume: true`: the service replays the missed events and nothing resyncs. A `stream.reset` as the resume's first event is `STREAM_RESET`: `expired`, `invalid` or `none` resyncs every store in place (`resyncProject`), `restarted` goes to `project-changed` and after the full load reads the new run ID (`refresh-status`, `STATUS_REFRESHED`). A status without `run_id` can't resume, so it reopens fresh and resyncs. Another run or project goes to `project-changed`, which asks `ConfirmProjectSwitch`, and on yes opens a fresh `/events` and runs `projectStore.reload(path)`, the full load that remounts the pages. On no, the stream stays closed, the pages stay visible but inert and dimmed (the `pages` wrapper in `+layout.svelte`), the service client holds every write but GETs and `/service/` routes with a `project_changed` error (`holdWrites`, set by `createConnectionStore` whenever the phase enters or leaves `project-changed`), and the banner offers `Load it` (`loadPending()`). `ConnectionBanner.svelte` (over the page in `+layout.svelte`) shows the banner, and `lib/connectionToasts.js` the drop and reconnect toasts. Deliberate reconnects (sharing, password changes) never go through `reconnecting`: see Sharing and passwords. Another client switching the project while connected (`FOLLOW_SWITCH` from the project store's standing listener, then `check-switch` reads the status and `SWITCH_CHECKED` acts on it) goes to the same `project-changed`, closing the stream, with `confirm-load {follow: true}` asking `ConfirmFollowProject` instead; a decline also calls `loadDeclined` (the followed opening screen closes). Both are refused unless `connected`, so a reconnect's load and a followed switch never both run (see `project-open.md`, "Another client's open").
- **Sharing and passwords (`lib/connection/ConnectionAccess.svelte`, `lib/connection/sharing.js`).** The rows after the service rows in `ConnectionDetail`. The password shows masked with reveal and copy for every connection, read only when asked (`LocalPairing(id).password` for a local one, `ConnectionPassword(id)` for a remote), never kept in a store. The store's `SHARE_LOCAL {address, port, host}`, `STOP_SHARING` (back to `127.0.0.1:0`), `SET_SHARE_HOST`, `ROTATE_PASSWORD` (`changePassword()` generates one) and `SET_NO_PASSWORD {origins}` set `busy`, close `/events` and `POST /service/control-listener/update`; then a remote's new password goes to the keychain (`store-password`) or its no-password state and the service's allowed origins to app config (`forget-password` → Go's `SetConnectionNoPassword`), and `rejoin` reaches the service again (the local one through `ConnectLocal`, whose `service control pair` gives the new address and password), resumes `/events` from the last event id (no resync), with the phase `connected` throughout; a drop while `busy` is ignored. Refusals: sharing is local-only, needs an IP to bind, a port 0–65535, and an IP in the code while the password is off (the service accepts only an IP Host then, and wants `no_password: true` to bind beyond loopback); turning the password off needs at least one origin (`isOrigin`, as Marasi checks), always adds the app's own origin (`APP_ORIGIN`, `location.origin`), and is refused while the code names a hostname or a remote is reached by hostname. `state.control` is `GET /service/control-listener/status` (read by `READ_CONTROL`, kept current by the `control_listener.*` events). Share picks among the service host's interfaces (`GET /listener/interfaces`, Tailscale's 100.64/10 address first), shows the pairing payload from Go's `LocalPairing(id)` (`service control pair`, since the service hands it out only on its socket) with the host override applied as `pair --host` does (`pairingWithHost`), and its QR code (`qrPath`, `qrcode-generator` at level M, UTF-8, quiet zone 4). Tests: `connectionSharing.test.js`, `sharing.test.js`, `app_sharing_test.go`.
- **Start Chrome (`chrome.go`, `frontend/src/lib/startChrome.js`).** The frontend reads `GET /listener/status` and `GET /certificate` through the service client and hands Go's `StartBrowser` a `ChromeStart {profile, connectionKind, connectionURL, proxyListener, spkiHash}`. Go aims Chrome at that listener (a wildcard bind becomes `127.0.0.1` on the local connection and the connection's host on a remote), pins the SPKI hash, and starts it through `launchChrome` (the Marasi library's launcher; tests replace it). Paths and profiles are this machine's, whatever the connection: `chrome_dirs` and `chrome_profiles` in Marasi's own `marasi_config.yaml`, shared with `marasi chrome …` and every service instance (`chrome_config.go`). Like Marasi's `service.Chrome`, every call takes `marasi_config.lock` (flock on unix, LockFileEx on Windows: `marasi_config_lock_*.go`), rereads the file, and writes back only the key it changed. Marasi's config directory is `App.marasiConfigDir`: the CLI config-dir override (`MARASI_APP_CLI_CONFIG_DIR`), else the app config directory. Deleting a profile removes its user-data directory under `chrome_profiles/` there. The app config holds no Chrome settings. The service's `chrome.*` events (another client, or `marasi chrome …` against the local instance) make Settings → Browser and Home reread the lists, but only on the local connection, since a remote's events describe the remote host's file (`lib/chromeConfigEvents.js`). Refusals carry `listener_inactive` or, on a remote whose listener binds loopback only, `listener_loopback`; `chromeErrorText` turns them into the toast. The service's `/chrome/*` routes are never called.
- **Extensions and Workshop (`stores/extensionsStore.js`).** `createExtensionsStore` keeps the list (`extensions`, each with `UICode` and `Version` from `GET /extension/{id}`'s `ui_code` and `version`, `""` when unset; `extension.updated` rereads them), each extension's GUI (`extensions_ui[name]`: renders by target plus `state`) from `GET /extension/{id}/ui` and the `extension.gui.rendered`/`.updated` events, and Workshop's code. A UI's button or menu action is `call(name, fn)` and leaving its page `sync(name)`, both `POST /extension/{id}/call` with the UI state as the one argument; a bound input is `edit(name, key, value)`, which a resync keeps until it is sent. `run(name, code)` is Workshop's `POST /extension/{id}` (runs, then stores). `watchLogs` feeds the logs drawer from `GET /extension/{id}/logs` and `extension.log`. Toasts an extension renders reach the layout's toast store through `showExtensionToasts`. The service has no lookup by name, so the store finds ids in its list. An extension with a web component draws it through `lib/extensions/WebComponent.svelte` (`webComponent.js`: ui_code registers `<name>-<target>-<version>`; the element gets `EventsOn` over `service.on` before it connects): the `icon` target on its rail tile when it draws no Lua `icon`, the `extension` target on its page. A new version draws a new element.
- **Startup.** `StartupRoutine2` (`+layout.svelte`) runs `readConfig`, then `connectionStore.start()`. On `connected`, the store opens `/events` and loads the service's project through `projectStore.loadService(path)` (`loadProject` in `stores/projectStore.js`), which names it and sets `loadedProject`. Opening and switching projects is `projectStore` (see `project-open.md`).

### Adding a store to the service client

Every store reaches the service the same way, as `homeStore` does:

1. **The adapter, `stores/xApi.js`:** `createXApi(client)` returns the `api` object `createXStore(api)` already takes. Each method calls `client.get/post/…` and maps the API's snake_case shapes to the shape the store reads (PascalCase today), so store logic and components barely change. Logic the Go binding did on top of Marasi (paging past 500, exclusions, empty note = delete) goes here or in a small pure helper beside it. Export the mappers stream events need too (`homeApi.js`'s `toLog`).
2. **The store, `stores/xStore.js`:** `export const xStore = createXStore(createXApi(service))`, importing `service` from `lib/service/index.js`, never a binding for service data. Route its events here: `service.on("log.added", homeStore.onLog)`, with the event name from `api.md`. Handlers get the event's parsed data as the service sends it.
3. **Load and resync:** register the store once, in its `xStore.js`, with `projectData` (`stores/projectData.js`): `projectData.register("x", {signal, clear, load, resync})`. `signal` is the opening screen's part (`loadSignals` in `lib/openProgress.js`), `clear` forgets the last project, `load` is its `populate()`, and `resync` reloads server data in place, keeping what only the app holds (drafts, selection, scroll, an open drawer); leave it out when the store holds nothing local, and `load` stands in. `loadProject` (`stores/projectStore.js`) clears and loads every registered store after a switch; `resyncProject` runs every `resync` after a stream reset (`expired`, `invalid`) on a reconnect to the same project. Remove the store's line from `resetProject` in `stores.js`. The store's module must be imported before the first load: `stores.js` imports the page stores today, and `projectStore.js` imports `homeStore.js`.
4. **Tests:** run `createXStore(createXApi(fakeClient))` with a fake client whose `get`/`post` answer from a route table, as `homeStore.test.js` does, so the mapping and the store are tested together through their public surface. Keep the store's existing fake-api suites. Add a `resync()` test proving it replaces server data and keeps the local state (Home's: the old counts stay until the new arrive).
5. **Errors:** a refusal the page acts on is read with `codeIDs` as before. If the app knew it by another code, add a row to `renames` in `lib/service/errors.js` with a case in `client.test.js`.
6. **No Wails events:** service data never comes through Go; subscribe with `service.on` in the store module.

## Marasi source

The app pins `github.com/tfkr-ae/marasi` in `go.mod`. A pair read (`GET /traffic/{id}`) asks only for what its reader shows, through `pairQuery` in `stores/trafficApi.js`: `RAW_ONLY` (`?prettified=false`) for copies, Launchpad and a drawer with Prettify off; `NO_BODIES` (`?raw=false&prettified=false`) for the Checkpoint item context and Logbook evidence rows; no parameters for a drawer with Prettify on, since a part without a prettified copy (a request with no body) shows raw and the parameters can't pick one part. Marasi before 4e3b8dc ignores them. `GOWORK=off go list -m -f '{{.Dir}}' github.com/tfkr-ae/marasi` gives that version's source. `~/Projects/marasi-project/marasi` is the sibling checkout, for unreleased changes.

## The Go shell

`App` holds no Marasi state. `newApp(configDir)` wires the desktop runtime, the local instance and the keychain; `NewApp` adds the app config. What Go keeps, by file:

- Dialogs, clipboard, events and quitting: `desktop.go`, `dialog.go`, `save_file.go`, and the quit and project-switch confirmation in `app.go` (`confirmLosingWork`: unsaved Launchpad drafts from `SetUnsavedDraftCount`, unsaved Logbook edits from `SetUnsavedLogbookEdits`, which `reportLogbookEdits` in `stores/logbookStore.js` keeps current from `hasUnsavedEdits`, and active Armory runs through `armory_guard.go`). Quitting, `ConfirmProjectSwitch` and `ConfirmFollowProject(project)` (`Stay` or `Load <project>`, for a project another client opened) all ask through it; the frontend opens the project on the service.
- Window and menu: `main.go`, `menu.go`.
- App updates: `update*.go`. Update requests skip a system proxy that is the local instance's proxy listener (`isMarasiListener`, reading `proxy_listener` from `service status` through `localProxyListener`, which tests replace).
- App config: `config.go`, `config_file.go` and one file per section (`keybindings.go`, `highlights.go`, `saved_queries.go`, `content_type_exclusion.go`, `connections.go`, `update_settings.go`, `cli_config.go`).
- The keychain: `keychain.go`. The Marasi CLI and the local instance: `cli*.go`, `local_instance.go`. Chrome: `chrome.go`, and its settings in Marasi's `marasi_config.yaml`: `chrome_config.go`.
- `OSUserName` (`os_user_name.go`), `GetBuildInfo` (`build_info.go`), `CopyCertToClipboard` and `OpenFileDialog` (`app.go`), `ReadUpstreamProxyCAFile` (`upstream_proxy.go`).

The Marasi module (`github.com/tfkr-ae/marasi`) is imported only for its `chrome` launcher package; which services the app supports is the API level range (see API level), not this version. Never import its proxy, repositories or `service` package: anything about projects, traffic or settings stored in a project is an API call from the frontend.

## Bindings

`main` registers `App` as the Wails v3 application's only service, so every exported `App` method in package `main` is callable from the frontend, whatever file it is in (`ServiceStartup` and `ServiceShutdown` are not). `wails3 generate bindings -d frontend/src/lib/bindings` generates JavaScript from them; frontend files import the calls from `frontend/src/lib/bindings/github.com/tfkr-ae/marasi-app/app.js`. That directory is gitignored and wiped on each run, so regenerate it (or run `scripts/bootstrap.sh`) after you add a method or change its signature. Run `wails3` with `GOWORK=off`, at the version `go.mod` pins.

A binding returns Go structs as instances of generated model classes, with the fields encoding/json gives them: a struct without json tags reaches JS with PascalCase field names. A field missing from the JSON gets its zero value, and a nil slice or map arrives as `[]` or `{}`. A Go error rejects the promise with a `RuntimeError` whose message is the `Error()` text. `runtime.js` makes a `RuntimeError` read as its message alone, so `String(err)` and template strings show the bare text, as in v2.

Add a binding only for what the Go shell does (above); anything the service serves is a service-client call. To add one: write the `App` method in its topic's file and test it on a fresh app config (`newTestApp` in `app_test.go`). Then regenerate the bindings, call the method from the topic's store or component, and keep the logic in a pure module that takes its API as an argument so `node --test` can run it.

## Desktop seams

`App` reaches the desktop runtime only through replaceable functions, which `useDesktopRuntime` in `desktop.go` points at the Wails application in `App.wails` (set by `main`, nil in tests). Nothing else calls Wails, so tests replace these, and a Wails upgrade changes only that file. Their option types (`messageDialogOptions`, `openDialogOptions`, `saveDialogOptions`, `fileFilter`) are the app's own, in `dialog.go`.

- `emitEvent` sends an event.
- `messageDialog` shows a message dialog and returns the pressed button's label. `showMessageDialog` waits for the pressed button's callback, and doesn't attach the dialog to the window, because a macOS sheet returns before the click. A `-tags server` build has no dialogs (`serverBuild`), so it answers the cancel button, or the button `MARASI_DIALOG_ANSWER` names (`serverDialogAnswer`, for verify-marasi). `nativeMessageDialog` (`dialog.go`) adapts confirmations for Windows and Linux.
- `openFileDialog` and `saveFileDialog` return the chosen path, or `""` when the user cancelled. `fileDialogResult` turns Windows' "cancelled by user" error into `""`. Callers treat `""` as a cancel and do nothing.
- `setClipboardText` puts text on the clipboard.
- `quitApp` calls the Wails application's `Quit`, which asks `shouldQuit` (the `ShouldQuit` option) on every OS, then runs `ServiceShutdown`.

**Quitting and closing.** `shouldQuit` runs on the main thread, so it never shows a dialog: it lets a quit go ahead when it is confirmed or would lose nothing, and otherwise refuses and asks in the background (`askThenQuit`), quitting again on a yes. The window's `WindowClosing` hook (`main.go`) calls `windowClosing`, which cancels the close and asks and quits the same way, so every OS shuts down through `Quit` (Wails issue #6368 skips shutdown when Windows closes the last window). `beforeClose` asks about unsaved work once per quit: after a confirmed quit or "Restart now", it lets Marasi close without asking again, and the quit's own closing of the window goes ahead. `askingToQuit` keeps it to one prompt at a time. `ServiceShutdown` calls `relaunchIfRestarting` last.

**The quit question (`quit_question.go`).** After the unsaved-work prompt, when any local connection has an owned run and the When quitting setting (app config `when_quitting`: `ask` by default, `keep` or `stop`; anything else reads as `ask`) is `ask`, `beforeClose` calls `askAboutOwnedRuns`. It emits `quit-question` with a `QuitQuestion {connections}`, the saved names of the owned runs' local connections (`ownedRunNames`; never a remote), and waits for `AnswerQuitQuestion(answer, remember)` as `cancelArmoryRuns` waits at quit, for at most `defaultQuitQuestionTimeout` (no answer keeps Marasi running). `cancel` keeps the app open, and the next quit asks again; `keep` and `stop` quit, and with `remember` save themselves as When quitting. `shouldQuit` lets a quit through at once only when it would neither lose work nor ask (`asksOnQuit`). `ServiceShutdown` stops owned runs only when `stopsOwnedRunsOnQuit`: never after "Restart now" (`restarting`), otherwise as this quit's answer said, or, without one, when When quitting is `stop`. In the frontend, `+layout.svelte` puts the `QuitQuestion` modal (`lib/connection/QuitQuestionModal.svelte`) in front of any open modal and answers through `quitAnswerOf` (`lib/connection/quitQuestion.js`), so closing it with Escape or the backdrop cancels. The modal is titled "Stop Marasi too?", lists the connections only when there are several (`namedConnections`), and has Keep running, Stop, Cancel and Don't ask again. Settings → Connection shows When quitting under the connection details (`ConnectionSettings.svelte`, choices in `WHEN_QUITTING`), saved through `SetFlag`. The server build, whose Wails server mode never asks `ShouldQuit`, quits as ⌘Q does on `SIGUSR1` (`server_quit_signal.go`), so verify-marasi can drive the question; `TERM` still shuts down without asking. Tests: `app_quit_question_test.go`; the ownership tests in `app_local_instance_test.go` quit with When quitting at `stop`.

**The window and menu.** `main.go` opens one window (Marasi, 1600×900, background RGB 27, 38, 54). On macOS, `applicationMenu` (`menu.go`) sets only the app and Edit menus, so Wails' default View and Window shortcuts don't fire over Marasi's. On Windows, `handleWailsError` (`wails_error_windows.go`) says so when the WebView2 runtime is missing, since the exe ships without an installer. The app sets no WebView2 resource filter (Wails issue #6530).

## Errors the frontend acts on

The frontend can only match error text, so an error it must act on carries a code: `<what>: <code>: <cause>`, or `<what>: <code> (<id>, <id>): <cause>` when it names items. Go builds them with `codedError` in `coded_error.go`, whose code constants carry doc comments (`cli_missing`, `instance_failed`, `instance_outdated`, `chrome_launch_failed`) and by hand (Chrome's `listener_inactive`, `listener_loopback`). The service client's `ServiceError` uses the same text for the service's refusals (see Service client). `codeIDs` in `frontend/src/lib/errorCodes.js` reads both, and helpers such as `launchPending.js` build on it. To handle a new Go refusal, add a code constant with a doc comment, wrap the error with `codedError`, then add a frontend helper that calls `codeIDs`.

## Events

- **Service to frontend.** The service's events reach the frontend over `/events` through the service client (`service.on(name, handler)`), never through Go. Each store subscribes in its `xStore.js` and applies the event in place, keeping what only the app holds (drafts, selection, scroll, the open drawer), so another client's change (the CLI, a phone, another app) shows without a resync. Bursts (bulk changes, rebuilds) are debounced (`EVENT_SETTLE_MS`, `SITEMAP_SETTLE_MS`, `LAUNCHPAD_SETTLE_MS`). Home's count refresh (`DASHBOARD_SETTLE_MS`) is a throttle instead: the first event starts the timer and later ones don't reset it, so steady traffic rereads the counts once per window. Apply the payload; read again only when it lacks the new values.
- **The event list.** `lib/service/events.js`'s `SERVICE_EVENTS` names every event Marasi publishes (its `service` package's `events.publish` calls). `events.test.js` scans `src/stores` and `src/lib` and fails when a name has no `.on(name` subscription, either `.on("name"` or a name in an array a file subscribes through a variable. Use full names, never a template string. When Marasi adds an event, add it to the list and subscribe to it. `stream.reset` and `stream.dropped` are the client's own (`STREAM_EVENTS`).

## Settings

- **App settings** are in `marasi_appconfig.yaml` in the config directory (`Config`, `LoadConfig` in `config.go`). Exported `Config` fields reach the frontend through `GetMarasiConfig`. Flags in `configDefaults` change through `ToggleFlag` and `SetFlag`. Other sections each have a key constant, a `parse*` function called from `LoadConfig`, and getters and setters that write through `writeConfigKeys` in `config_file.go`.
- **Per-project settings** are client settings in the open project on the service, under the client `marasi-app` (`stores/clientSettingsApi.js`'s `createClientSettings`, over `/client-settings/marasi-app`). Stores use it with their own key prefixes.
- **App default with a project override.** `content_type_exclusion.go` is the pattern, from [Ledger settings are app defaults with project overrides, stored by the app](../../adr/2026-10-16-app-defaults-with-project-overrides.md).
- `marasi_config.yaml` is Marasi's own config, which service instances share. The app neither reads nor writes it.
- **Upstream proxies** (`stores/upstreamProxyApi.js`). The list is the service host's (its `marasi_config.yaml`) and the selection the open project's, both through the `/upstream-proxy` routes and `PUT /upstream-proxy-selection`. Writes answer with the items alone, so the adapter reads the list again for the selection. It builds an update itself (`upstreamProxyUpdate`: a URL, a new CA, or `ca: null` to remove it) and refuses one that changes nothing. Once Settings has read the list, `upstream_proxy.*` events and a reconnect read it again. Choosing a CA file stays Go (`ReadUpstreamProxyCAFile`). A selection the service host doesn't list fails the project's traffic closed, and `configured` reports it.
- **Jobs** (`stores/jobsApi.js`): `GET /jobs` and `POST /jobs/{name}/rebuild`; the rebuildable set (`REBUILDABLE_JOBS`) is the app's, since the service doesn't report it. `job.progress` updates the running job's row at once (`onProgress`), and `job.complete` reads the list again. The service publishes progress once per 1 MiB batch, after an interval, so a small rebuild shows only the completion.
- **Certificate** (`lib/certificate.js`): Download and Copy Certificate read `GET /certificate` and hand the PEM to Go: `SaveFileAs` (`save_file.go`, the native save dialog for any bytes the frontend fetched, shared with the Logbook) or `CopyCertToClipboard(pem)`.
