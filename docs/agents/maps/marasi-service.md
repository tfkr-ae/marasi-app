# The marasi service

How the app reaches a Marasi service, how Go and the frontend talk (bindings, events, errors), and where app and project settings live. Names are functions, types and files, so search for them.

## The shape

Every page works against a Marasi service instance through its control API and its `/events` stream (`.scratch/service-implementation/spec.md`). The frontend's service client makes every API call and the connection store keeps the connection; Go is a desktop shell (see "The Go shell") and never opens a project, runs a proxy or reads a repository. Startup opens no project and starts no listener in process.

## The service side

- **Local instance (Go, `local_instance.go`).** `ConnectLocal` finds the Marasi CLI (`findCLI`, see Marasi CLI below), runs `service status --json`, and either starts the `default` instance (`service start --address <default_address> --port <default_port> --control-address 127.0.0.1:0`, retried once with `--port 0` when the port is taken (`portTaken`), a generated password in `MARASI_PASSWORD`, never in the arguments) or attaches, turning a control listener on with `service control start` when it has none. It reads the address and password back from `service control pair` over the socket, and returns `LocalConnection {url, password, instance, startedByApp}`. `ServiceShutdown` stops the instance only when the app started it (`stopOwnedLocal`). Every call goes through `runCLI`, `findCLI` and `newPassword`, which tests replace (`app_local_instance_test.go`'s `fakeCLI`), passes `--config-dir` from `MARASI_APP_CLI_CONFIG_DIR` when set, and drops inherited `MARASI_*` variables. Failures carry the `cli_missing` or `instance_failed` code, or `instance_outdated` when the running instance answers a control route with 404 (an older Marasi, such as the v2 app's bundled build, without pairing); its cause names the running version. `RestartLocalInstance` stops that instance and starts its project again through the same start path, so the app owns it; `lib/connection/OutdatedInstance.svelte` offers it (with a confirm) in `ConnectionDetail` and on the startup failure screen, and `outdatedVersion` (`cli.js`) reads the version.
- **Marasi CLI (`cli.go`, `cli_config.go`, `cli_locate.go`, `cli_install.go`; ADR `2026-11-06-the-marasi-cli-is-never-bundled`).** `LocateCLI` tries `cli_path` in app config, then `marasi` on PATH, and accepts a candidate only when its `service status --json` answers as Marasi does; version and channel come from the binary's Go build info (`-X main.version`/`main.buildChannel`), never by running it. `UseCLIPath` probes before saving (`cli_path_source: custom`), `ClearCLIPath` goes back to PATH, `BrowseCLIPath` is the file dialog. `InstallCLI(dir)` and `CheckForCLIUpdate` read the release on the CLI channel (`cli_channel`: absent follows the app, a dev app follows release; `SetCLIChannel("app"|"release"|"nightly")`), verify `checksums.txt.minisig` with `marasiCLIPublicKey` and a trusted comment of exactly `marasi <channel> <version>`, then the asset's SHA-256, and only then copy it beside the target (emitting `cli-install-progress` `{step: download|verify|install, received, total}` throughout, which `CLIProgress.svelte` shows), rename it in and `chmod 0755` (not on Windows), saving `cli_path_source: installed`. Assets: `marasi-darwin-arm64`, `marasi-linux-amd64`, `marasi-windows-amd64.exe`; any other platform fails `no-build` before asking GitHub. Every effect goes through `App.cliRuntime`, which `cli_install_test.go` and `cli_locate_test.go` replace (fake release server, test key). Frontend: `lib/connection/cli.js` (pure), `CLISetup.svelte` (in `ConnectionDetail` on `cli_missing`; `+layout.svelte` opens the Connections modal by itself once per such failure) and `CLISettings.svelte` (Settings → Marasi CLI).
- **Service client (`frontend/src/lib/service/`).** `client.js`'s `createServiceClient({fetch, EventSource})` is the only code that calls `fetch` for the service: `use({url, password})`, `get`/`post`/`put`/`del`/`request`, `on(eventName, handler)` (returns its unsubscribe), `openEvents({onOpen, onDrop})` and `closeEvents()`. For the routes that aren't JSON, `request(method, path, {raw, contentType})` sends bytes (an artifact) and `{as: "bytes"}` resolves to the answer's bytes (artifact content, a report); `SaveFileAs` (`save_file.go`) saves such bytes through the native Save dialog. It sends `Authorization: Bearer` unless the connection has no password. `errors.js` turns a refusal into a `ServiceError` whose text is `"<METHOD> <path>: <code>[ (<ids>)]: <message>"`, so `codeIDs` and its helpers read it; its `renames` table maps service codes the app knew by another name (`project_already_open` → `project_locked`, a 404 on a Checkpoint forward or drop → `checkpoint_gone (<id>)`, a 404 on a launchpad unlink → `not_linked`). A non-JSON refusal is `http_error` with `status`. `sse.js` is the production EventSource: a fetch-stream reader, since a native `EventSource` can't send the password. `index.js` exports the app's client, `service`. Tests: `client.test.js`, `sse.test.js`.
- **Connection store (`stores/createConnectionStore.js`, bound in `connectionStore.js`).** A pure `reduce(state, action)` returns `{state, steps, refusal}`, and the store performs the steps through its `api` (Go's `ConnectLocal`, the service client, `loadProject`, `resyncProject`, `ConfirmProjectSwitch` and `projectStore.reload`) and its `timers`. Phases: `idle`, `starting`, `connecting`, `connected`, `failed` (Retry begins again), `reconnecting` and `project-changed`. A new phase or event is a case in `reduce`, a step in `perform`, and a scenario in `connectionStore.test.js`. The password passes through steps and never sits in the state.
- **Saved connections (`connections.go`, `keychain.go`).** `marasi_appconfig.yaml` keeps `connections` (id, name, kind, URL, `no_password`, `password_ref`), `active_connection` and `recent_projects` per connection id; never a password. `AddConnection`, `SetConnectionAddress`, `SetConnectionPassword`, `RemoveConnection` (not the local or active one; drops its password and recents), `SetActiveConnection`, `RecentProjects` and `AddRecentProject` are the bindings. Passwords go to the OS keychain on release builds and otherwise, or when the keychain refuses, to `marasi_app_passwords.json` (`0600`) beside the config; the ref says which (`keychain:`/`file:`). Tests: `app_connections_test.go`. The store's `CONNECTIONS_LOADED`, `SWITCH_CONNECTION` (guarded by `ConfirmProjectSwitch`, then close `/events`, `set-active`, `clear-stores`, begin), `AUTH_REJECTED` (phase `auth-failed`, no timer) and `ENTER_PASSWORD` cover remotes (`connectionRemote.test.js`); `stores/recentProjects.js` adds each newly loaded project to the active connection's recents.
- **Version warning.** Go's `MarasiPin` (`marasi_pin.go`) returns the date of the `github.com/tfkr-ae/marasi` pseudo-version Go recorded in the binary at build time (so it follows `go.mod`), as `DD.MM.YYYY`. `connectionStore.js` hands it to the store as `MARASI_PIN`; `CONNECTED` and `RECONNECTED` set `versionWarning` when the service's version date (`DD.MM.YYYY`, `DD.MM.YYYY-suffix` or `DD.MM.YYYY (nightly <sha>)`) is older. `dev` and a build without a pin never warn. `ConnectionBanner.svelte` and `ConnectionDetail.svelte` show it; it never blocks.
- **Reconnect.** A dropped `/events` (a network failure, a restart, or the service dropping a subscriber whose queue overflowed, which looks the same) is `STREAM_DROPPED`: `reconnecting`, `attempt` + 1, and a `wait` of `backoff(attempt)` (1 s doubling to 30 s). The wait's end or `retryNow()` (the banner's Retry now) is `RECONNECT_NOW`, which reaches the local instance through `ConnectLocal` again (its control address can change) and reads `/service/status`; a failure is another drop. `RECONNECTED` compares the status with `state.project` (kept current by `PROJECT_LOADED`, which `connectionStore.js` dispatches from `loadedProject`) and `state.version`, and treats as a restart a `service.restarting` seen before the drop (`SERVICE_RESTARTING`), a new version, or the service gone meanwhile: `ConnectLocal` reports `wasStopped` (it found the instance not running), or an attempt got no HTTP answer (`serviceGone`). `/service/status` names nothing that changes per process (decisions ruling 2), so a restart quicker than the backoff, at the same version and without the event, still resyncs in place. The same project resyncs every store in place (`resyncProject`); otherwise `project-changed` asks `ConfirmProjectSwitch`, and on yes opens `/events` and runs `projectStore.reload(path)`, the full load that remounts the pages. On no, the stream stays closed, the pages stay visible but inert and dimmed (the `pages` wrapper in `+layout.svelte`), the service client holds every write but GETs and `/service/` routes with a `project_changed` error (`holdWrites`, set by `createConnectionStore` whenever the phase enters or leaves `project-changed`), and the banner offers `Load it` (`loadPending()`). `ConnectionBanner.svelte` (over the page in `+layout.svelte`) shows the banner, and `lib/connectionToasts.js` the drop and reconnect toasts. Deliberate reconnects (sharing, password changes) never go through `reconnecting`: see Sharing and passwords.
- **Sharing and passwords (`lib/connection/ConnectionAccess.svelte`, `lib/connection/sharing.js`).** The rows after the service rows in `ConnectionDetail`. The password shows masked with reveal and copy for every connection, read only when asked (`LocalPairing().password` for the local one, `ConnectionPassword(id)` for a remote), never kept in a store. The store's `SHARE_LOCAL {address, port, host}`, `STOP_SHARING` (back to `127.0.0.1:0`), `SET_SHARE_HOST`, `ROTATE_PASSWORD` (`changePassword()` generates one) and `SET_NO_PASSWORD {origins}` set `busy`, close `/events` and `POST /service/control-listener/update`; then a remote's new password goes to the keychain (`store-password`) or its no-password state and the service's allowed origins to app config (`forget-password` → Go's `SetConnectionNoPassword`), and `rejoin` reaches the service again (the local one through `ConnectLocal`, whose `service control pair` gives the new address and password), reopens `/events` and resyncs, with the phase `connected` throughout; a drop while `busy` is ignored. Refusals: sharing is local-only, needs an IP to bind, a port 0–65535, and an IP in the code while the password is off (the service accepts only an IP Host then, and wants `no_password: true` to bind beyond loopback); turning the password off needs at least one origin (`isOrigin`, as Marasi checks), always adds the app's own origin (`APP_ORIGIN`, `location.origin`), and is refused while the code names a hostname or a remote is reached by hostname. `state.control` is `GET /service/control-listener/status` (read by `READ_CONTROL`, kept current by the `control_listener.*` events). Share picks among the service host's interfaces (`GET /listener/interfaces`, Tailscale's 100.64/10 address first), shows the pairing payload from Go's `LocalPairing` (`service control pair`, since the service hands it out only on its socket) with the host override applied as `pair --host` does (`pairingWithHost`), and its QR code (`qrPath`, `qrcode-generator` at level M, UTF-8, quiet zone 4). Tests: `connectionSharing.test.js`, `sharing.test.js`, `app_sharing_test.go`.
- **Start Chrome (`chrome.go`, `frontend/src/lib/startChrome.js`).** The frontend reads `GET /listener/status` and `GET /certificate` through the service client and hands Go's `StartBrowser` a `ChromeStart {profile, connectionKind, connectionURL, proxyListener, spkiHash}`. Go aims Chrome at that listener (a wildcard bind becomes `127.0.0.1` on the local connection and the connection's host on a remote), pins the SPKI hash, and starts it through `launchChrome` (the Marasi library's launcher; tests replace it). Paths and profiles are this machine's, whatever the connection: `chrome_dirs` and `chrome_profiles` in Marasi's own `marasi_config.yaml`, shared with `marasi chrome …` and every service instance (`chrome_config.go`). Like Marasi's `service.Chrome`, every call takes `marasi_config.lock` (flock on unix, LockFileEx on Windows: `marasi_config_lock_*.go`), rereads the file, and writes back only the key it changed. Marasi's config directory is `App.marasiConfigDir`: the CLI config-dir override (`MARASI_APP_CLI_CONFIG_DIR`), else the app config directory. Deleting a profile removes its user-data directory under `chrome_profiles/` there. The app config holds no Chrome settings. Refusals carry `listener_inactive` or, on a remote whose listener binds loopback only, `listener_loopback`; `chromeErrorText` turns them into the toast. The service's `/chrome/*` routes are never called.
- **Extensions and Workshop (`stores/extensionsStore.js`).** `createExtensionsStore` keeps the list (`extensions`, with `WebUI` when the Lua defines `ui_code`), each extension's GUI (`extensions_ui[name]`: renders by target plus `state`) from `GET /extension/{id}/ui` and the `extension.gui.rendered`/`.updated` events, and Workshop's code. A UI's button or menu action is `call(name, fn)` and leaving its page `sync(name)`, both `POST /extension/{id}/call` with the UI state as the one argument; a bound input is `edit(name, key, value)`, which a resync keeps until it is sent. `run(name, code)` is Workshop's `POST /extension/{id}` (runs, then stores). `watchLogs` feeds the logs drawer from `GET /extension/{id}/logs` and `extension.log`. Toasts an extension renders reach the layout's toast store through `showExtensionToasts`. The service has no lookup by name, so the store finds ids in its list. An extension with a web component UI gets a disabled rail tile (`WebUITile.svelte`).
- **Startup.** `StartupRoutine2` (`+layout.svelte`) runs `readConfig`, then `connectionStore.start()`. On `connected`, the store opens `/events` and loads the service's project through `loadProject` in `stores/projectStore.js`, then `projectStore.loaded(path)` names it and sets `loadedProject`. Opening and switching projects is `projectStore` (see `project-open.md`).

### Adding a store to the service client

Every store reaches the service the same way, as `homeStore` does:

1. **The adapter, `stores/xApi.js`:** `createXApi(client)` returns the `api` object `createXStore(api)` already takes. Each method calls `client.get/post/…` and maps the API's snake_case shapes to the shape the store reads (PascalCase today), so store logic and components barely change. Logic the Go binding did on top of Marasi (paging past 500, exclusions, empty note = delete) goes here or in a small pure helper beside it. Export the mappers stream events need too (`homeApi.js`'s `toLog`).
2. **The store, `stores/xStore.js`:** `export const xStore = createXStore(createXApi(service))`, importing `service` from `lib/service/index.js`, never a binding for service data. Route its events here: `service.on("log.added", homeStore.onLog)`, with the event name from `api.md`. Handlers get the event's parsed data as the service sends it.
3. **Load and resync:** register the store once, in its `xStore.js`, with `projectData` (`stores/projectData.js`): `projectData.register("x", {signal, clear, load, resync})`. `signal` is the opening screen's part (`loadSignals` in `lib/openProgress.js`), `clear` forgets the last project, `load` is its `populate()`, and `resync` reloads server data in place, keeping what only the app holds (drafts, selection, scroll, an open drawer); leave it out when the store holds nothing local, and `load` stands in. `loadProject` (`stores/projectStore.js`) clears and loads every registered store after a switch; `resyncProject` runs every `resync` after a reconnect to the same project. Remove the store's line from `resetProject` in `stores.js`. The store's module must be imported before the first load: `stores.js` imports the page stores today, and `projectStore.js` imports `homeStore.js`.
4. **Tests:** run `createXStore(createXApi(fakeClient))` with a fake client whose `get`/`post` answer from a route table, as `homeStore.test.js` does, so the mapping and the store are tested together through their public surface. Keep the store's existing fake-api suites. Add a `resync()` test proving it replaces server data and keeps the local state (Home's: the old counts stay until the new arrive).
5. **Errors:** a refusal the page acts on is read with `codeIDs` as before. If the app knew it by another code, add a row to `renames` in `lib/service/errors.js` with a case in `client.test.js`.
6. **No Wails events:** service data never comes through Go; subscribe with `service.on` in the store module.

## Marasi source

The app pins `github.com/tfkr-ae/marasi` in `go.mod`. `GOWORK=off go list -m -f '{{.Dir}}' github.com/tfkr-ae/marasi` gives that version's source. `~/Projects/marasi-project/marasi` is the sibling checkout, for unreleased changes.

## The Go shell

`App` holds no Marasi state. `newApp(configDir)` wires the desktop runtime, the local instance and the keychain; `NewApp` adds the app config. What Go keeps, by file:

- Dialogs, clipboard, events and quitting: `desktop.go`, `dialog.go`, `save_file.go`, and the quit and project-switch confirmation in `app.go` (`confirmLosingWork`: unsaved Launchpad drafts from `SetUnsavedDraftCount`, active Armory runs through `armory_guard.go`). `ConfirmProjectSwitch` is that prompt; the frontend opens the project on the service.
- Window and menu: `main.go`, `menu.go`.
- App updates: `update*.go`. Update requests skip a system proxy that is the local instance's proxy listener (`isMarasiListener`, reading `proxy_listener` from `service status` through `localProxyListener`, which tests replace).
- App config: `config.go`, `config_file.go` and one file per section (`keybindings.go`, `highlights.go`, `saved_queries.go`, `content_type_exclusion.go`, `connections.go`, `update_settings.go`, `cli_config.go`).
- The keychain: `keychain.go`. The Marasi CLI and the local instance: `cli*.go`, `local_instance.go`. Chrome: `chrome.go`, and its settings in Marasi's `marasi_config.yaml`: `chrome_config.go`.
- `OSUserName` (`os_user_name.go`), `MarasiPin` (`marasi_pin.go`), `GetBuildInfo` (`build_info.go`), `CopyCertToClipboard` and `OpenFileDialog` (`app.go`), `ReadUpstreamProxyCAFile` (`upstream_proxy.go`).

The Marasi module (`github.com/tfkr-ae/marasi`) is imported only for its `chrome` launcher package; its pinned version also dates the oldest service the app supports (`MarasiPin`). Never import its proxy, repositories or `service` package: anything about projects, traffic or settings stored in a project is an API call from the frontend.

## Bindings

`main` registers `App` as the Wails v3 application's only service, so every exported `App` method in package `main` is callable from the frontend, whatever file it is in (`ServiceStartup` and `ServiceShutdown` are not). `wails3 generate bindings -d frontend/src/lib/bindings` generates JavaScript from them; frontend files import the calls from `frontend/src/lib/bindings/github.com/tfkr-ae/marasi-app/app.js`. That directory is gitignored and wiped on each run, so regenerate it (or run `scripts/bootstrap.sh`) after you add a method or change its signature. Run `wails3` with `GOWORK=off`, at the version `go.mod` pins.

A binding returns Go structs as instances of generated model classes, with the fields encoding/json gives them: a struct without json tags reaches JS with PascalCase field names. A field missing from the JSON gets its zero value, and a nil slice or map arrives as `[]` or `{}`. A Go error rejects the promise with a `RuntimeError` whose message is the `Error()` text. `runtime.js` makes a `RuntimeError` read as its message alone, so `String(err)` and template strings show the bare text, as in v2.

Add a binding only for what the Go shell does (above); anything the service serves is a service-client call. To add one: write the `App` method in its topic's file and test it on a fresh app config (`newTestApp` in `app_test.go`). Then regenerate the bindings, call the method from the topic's store or component, and keep the logic in a pure module that takes its API as an argument so `node --test` can run it.

## Desktop seams

`App` reaches the desktop runtime only through replaceable functions, which `useDesktopRuntime` in `desktop.go` points at the Wails application in `App.wails` (set by `main`, nil in tests). Nothing else calls Wails, so tests replace these, and a Wails upgrade changes only that file. Their option types (`messageDialogOptions`, `openDialogOptions`, `saveDialogOptions`, `fileFilter`) are the app's own, in `dialog.go`.

- `emitEvent` sends an event.
- `messageDialog` shows a message dialog and returns the pressed button's label. `showMessageDialog` waits for the pressed button's callback, and doesn't attach the dialog to the window, because a macOS sheet returns before the click. A `-tags server` build has no dialogs (`serverBuild`), so it answers the cancel button. `nativeMessageDialog` (`dialog.go`) adapts confirmations for Windows and Linux.
- `openFileDialog` and `saveFileDialog` return the chosen path, or `""` when the user cancelled. `fileDialogResult` turns Windows' "cancelled by user" error into `""`. Callers treat `""` as a cancel and do nothing.
- `setClipboardText` puts text on the clipboard.
- `quitApp` calls the Wails application's `Quit`, which asks `shouldQuit` (the `ShouldQuit` option) on every OS, then runs `ServiceShutdown`.

**Quitting and closing.** `shouldQuit` runs on the main thread, so it never shows a dialog: it lets a quit go ahead when it is confirmed or would lose nothing, and otherwise refuses and asks in the background (`askThenQuit`), quitting again on a yes. The window's `WindowClosing` hook (`main.go`) calls `windowClosing`, which cancels the close and asks and quits the same way, so every OS shuts down through `Quit` (Wails issue #6368 skips shutdown when Windows closes the last window). `beforeClose` asks about unsaved work once per quit: after a confirmed quit or "Restart now", it lets Marasi close without asking again, and the quit's own closing of the window goes ahead. `askingToQuit` keeps it to one prompt at a time. `ServiceShutdown` calls `relaunchIfRestarting` last.

**The window and menu.** `main.go` opens one window (Marasi, 1600×900, background RGB 27, 38, 54). On macOS, `applicationMenu` (`menu.go`) sets only the app and Edit menus, so Wails' default View and Window shortcuts don't fire over Marasi's. On Windows, `handleWailsError` (`wails_error_windows.go`) says so when the WebView2 runtime is missing, since the exe ships without an installer. The app sets no WebView2 resource filter (Wails issue #6530).

## Errors the frontend acts on

The frontend can only match error text, so an error it must act on carries a code: `<what>: <code>: <cause>`, or `<what>: <code> (<id>, <id>): <cause>` when it names items. Go builds them with `codedError` in `coded_error.go`, whose code constants carry doc comments (`cli_missing`, `instance_failed`, `instance_outdated`, `chrome_launch_failed`) and by hand (Chrome's `listener_inactive`, `listener_loopback`). The service client's `ServiceError` uses the same text for the service's refusals (see Service client). `codeIDs` in `frontend/src/lib/errorCodes.js` reads both, and helpers such as `launchPending.js` build on it. To handle a new Go refusal, add a code constant with a doc comment, wrap the error with `codedError`, then add a frontend helper that calls `codeIDs`.

## Events

- **Service to frontend.** The service's events reach the frontend over `/events` through the service client (`service.on(name, handler)`), never through Go.
- **Go to frontend.** Go's own events (`update-available`, `update-progress`, `update-installed`, `update-failed`, `cli-install-progress`, `armory-cancel-runs`) go through `a.emitEvent`, which tests replace (`recordedEvents` in `app_test.go`).
- **The frontend's runtime module.** `frontend/src/lib/runtime.js` is the only frontend file that calls the Wails runtime (`@wailsio/runtime`, pinned to the Go module's version) for anything that isn't a binding: `on`, `once`, `off`, `emit`, `setWindowTitle` and `openURL`. Wails hands a listener a `{name, data}` event; a subscriber's callback receives `data`, the payload: the value Go emitted, or `null` when it sent none. `on` and `once` return a function that removes that one listener, and `off` removes every listener for a name. Import from it, never from `@wailsio/runtime`. `runtime.test.js` runs it against a fake runtime.
- **Frontend subscriptions** are in `onMount` in `frontend/src/routes/+layout.svelte`, which forwards each event to a store's `on*` method. Add the matching `off` to its cleanup.
- **Frontend to Go.** Nothing; extension UIs call the service through `extensionsStore` (above).

## Settings

- **App settings** are in `marasi_appconfig.yaml` in the config directory (`Config`, `LoadConfig` in `config.go`). Exported `Config` fields reach the frontend through `GetMarasiConfig`. Flags in `configDefaults` change through `ToggleFlag` and `SetFlag`. Other sections each have a key constant, a `parse*` function called from `LoadConfig`, and getters and setters that write through `writeConfigKeys` in `config_file.go`.
- **Per-project settings** are client settings in the open project on the service, under the client `marasi-app` (`stores/clientSettingsApi.js`'s `createClientSettings`, over `/client-settings/marasi-app`). Stores use it with their own key prefixes.
- **App default with a project override.** `content_type_exclusion.go` is the pattern, from [Ledger settings are app defaults with project overrides, stored by the app](../../adr/2026-10-16-app-defaults-with-project-overrides.md).
- `marasi_config.yaml` is Marasi's own config, which service instances share. The app neither reads nor writes it.
- **Upstream proxies** (`stores/upstreamProxyApi.js`). The list is the service host's (its `marasi_config.yaml`) and the selection the open project's, both through the `/upstream-proxy` routes and `PUT /upstream-proxy-selection`. Writes answer with the items alone, so the adapter reads the list again for the selection. It builds an update itself (`upstreamProxyUpdate`: a URL, a new CA, or `ca: null` to remove it) and refuses one that changes nothing. Once Settings has read the list, `upstream_proxy.*` events and a reconnect read it again. Choosing a CA file stays Go (`ReadUpstreamProxyCAFile`). A selection the service host doesn't list fails the project's traffic closed, and `configured` reports it.
- **Jobs** (`stores/jobsApi.js`): `GET /jobs` and `POST /jobs/{name}/rebuild`; the rebuildable set (`REBUILDABLE_JOBS`) is the app's, since the service doesn't report it.
- **Certificate** (`lib/certificate.js`): Download and Copy Certificate read `GET /certificate` and hand the PEM to Go: `SaveFileAs` (`save_file.go`, the native save dialog for any bytes the frontend fetched, shared with the Logbook) or `CopyCertToClipboard(pem)`.
